# Colocated hooks 설계 (GAP-032, #71)

> 상태: **결정됐고 구현됐다.** 2026-09-12. §5의 셋에 대한 답은 §4의 권장안 그대로다 —
> 앱의 static, 파일이 자기 이름을 쓰기, 모든 페이지에 전부. §7이 제안한 순서대로
> `examples/hooks`와 그 E2E를 먼저 만들었고, 그 과정에서 §2-(가)의 경합이 재현됐다.
> 사용법은 [features/hooks.md](../features/hooks.md).

## 1. 무엇을 푸는 문제인가

훅을 쓰려면 세 곳을 챙겨야 한다.

1. 템플릿에 `wire-hook="Chart"`
2. 서버에 `handle_hook_event` (훅이 서버와 말할 때만)
3. **어딘가에서** `window.wireview.hooks.Chart = {...}`

세 번째를 잊었을 때 일어나는 일은 브라우저 콘솔의 `console.warn` 한 줄이다
(`wireview.js`의 `mountHooks`). 서버 로그에도, `manage.py check`에도, 페이지에도 아무것도
나타나지 않는다. 컴포넌트는 정상으로 보이고 훅만 조용히 없다.

컴포넌트 하나를 다른 프로젝트로 옮길 때 세 번째가 따라가지 않는 것도 같은 문제의 다른 얼굴이다.

## 2. 지금 실제로 무슨 일이 일어나는가

착수 전에 알아야 하는 것이 셋 있고, 셋 다 이슈 본문에 없다.

**(가) 등록은 join 전에 끝나 있어야 한다.** 훅은 join *응답*이 온 뒤에 마운트되지만
(`wireview.js`의 "Initialize hooks after joining"), `window.wireview.hooks`를 채우는 스크립트가
그때까지 실행되지 않았으면 그 훅은 없는 것이다. 그리고 번들은 `defer`로 실려 **실행 즉시
`connection.open()`을 부른다.** 즉 소켓은 이미 열리는 중이다.

`defer` 스크립트는 문서 순서대로, **`DOMContentLoaded` 전에** 실행된다. 그러니 번들 뒤에 붙는
`<script defer>`는 순서가 보장되지만, 소켓이 열리는 시점과의 순서는 보장되지 않는다 — 훅 파일을
받아오는 것이 느리고 WebSocket 핸드셰이크가 빠르면 `joinAllComponents()`가 먼저 돈다.

**이것은 지금 고칠 수 있고, 고치면 모든 후보가 쉬워진다**: `joinAllComponents()`를
`DOMContentLoaded` 뒤로 미루면 `defer` 스크립트 전부가 그 전에 실행됨이 **명세로 보장된다.**
비동기 import도, 준비 신호도 필요 없어진다.

**(나) boost는 body만 갈아 끼운다.** `replaceBodyContent(doc.body)` — 새 문서의 `<head>`에 있던
`<script>`는 실행되지 않는다. 그러므로 **페이지가 쓰는 훅만 그 페이지에 내보내면, 경계 안에서
boost로 이동한 목적지에는 그 훅이 없다.** 첫 로드에서는 되고 이동해서 들어가면 안 되는, 가장
나쁜 종류의 결함이다.

경계를 *넘는* 이동은 전체 로드라 괜찮다(#58). 문제는 경계 **안**의 이동이고, 그것이 boost가
존재하는 이유다.

**(다) 헤더 태그는 이미 요청에 의존한다.** `{% wireview_header %}`는 `takes_context=True`이고
`context["request"]`에서 경계 이름을 읽는다. 없으면 기능이 통째로 조용히 꺼지고, 그것을
`wireview.W010`이 잡는다. 훅 수집을 **요청에 의존하게** 만들면 같은 조용한 실패를 하나 더 만든다.

그런데 (나)가 이미 답을 준다 — **훅 목록은 페이지의 성질이 아니라 프로젝트의 성질이어야 한다.**
프로젝트 전역이면 요청과 무관하게 기동 때 한 번 정해지고, 새 의존은 생기지 않는다.

## 3. 후보 셋

이슈가 적은 셋을, (가)~(다)를 알고 다시 읽는다.

### A. 규약 경로를 앱의 static에 두고 헤더가 수집한다

`<app>/static/<app_label>/hooks/*.js`. 기동 때 앱 레지스트리를 돌며 파일 목록을 만들고,
`{% wireview_header %}`가 `{% static %}`으로 해석한 `<script defer>`를 **모든 페이지에** 내보낸다.

| | |
|---|---|
| 빌드 단계 | 없음 |
| collectstatic·해시 | `{% static %}`을 거치므로 `ManifestStaticFilesStorage`가 그대로 동작한다 |
| 캐시 무효화 | 위와 같음. 파일이 바뀌면 해시가 바뀐다 |
| 순서 | (가)를 고치면 명세로 보장 |
| boost | 전부 내보내므로 (나)가 없다 |
| 대가 | 훅 파일 수만큼 `<script>` 태그가 는다. 20개면 20개다 |

"컴포넌트 파일 옆"은 아니다. **앱 옆**이다. Phoenix는 컴포넌트 소스 파일 안에 훅을 적고
컴파일 때 뽑아내는데, Django에는 그 컴파일 단계가 없다.

### B. 컴포넌트 클래스가 `_hooks = {...}`로 선언한다

서버가 그 컴포넌트에 필요한 훅의 경로를 안다.

| | |
|---|---|
| 좋은 점 | `manage.py check`가 선언과 파일을 곧바로 대조할 수 있다 (AC2가 쉬워진다) |
| 나쁜 점 | **템플릿의 `wire-hook=`이 이미 같은 말을 한다.** 두 곳이 어긋날 수 있고, 어긋나면 조용하다 |
| 나쁜 점 | 조건부로 렌더되는 훅은 선언에서 빠지기 쉽다 |
| 치명 | 페이지가 쓰는 것만 내보내는 설계로 자연히 흘러간다 → **(나)에 정면으로 걸린다** |

전역으로 내보낼 거라면 컴포넌트별 선언은 값을 잃는다. 남는 값은 체크 하나인데, 그것은 A에서
템플릿을 훑어도 얻을 수 있다(§4).

### C. `manage.py wireview_hooks`가 번들 진입점을 만든다

`wireview_stubs`·`wireview_lsp`와 같은 결의 명령.

| | |
|---|---|
| 좋은 점 | 유일하게 **진짜 번들링**을 준다. 요청 수가 늘지 않고 minify도 된다 |
| 대가 | **프로젝트에 JS 빌드 단계를 요구한다.** wireview가 지금까지 요구하지 않은 것이고, `{% wireview_header %}`가 완성된 번들 하나를 싣는 것이 이 라이브러리의 형태다 |
| 그리고 | 번들러가 이미 있는 프로젝트는 **오늘도 이걸 손으로 할 수 있다.** 라이브러리가 없어서 못 하는 일이 아니다 |

C는 A와 배타적이지 않다. A를 기본으로 두고, 번들을 쓰는 프로젝트는 수집을 끄고 자기 번들에
같은 파일들을 넣으면 된다.

## 4. 권하는 것

**A + (가)를 고치는 것.** 구체적으로:

1. `joinAllComponents()`를 `DOMContentLoaded` 뒤로 미룬다. 이것 하나로 "훅은 첫 join 전에
   등록되어 있다"가 **명세로 보장되는 계약**이 된다. (`tests/js/`에 순수 함수로 떼어 낼 수 있는
   판단은 아니므로, E2E로 고정한다.)
2. 기동 때 앱 레지스트리를 돌아 `<app>/static/<app_label>/hooks/*.js`를 모은다. **요청과 무관**하고
   프로젝트 전역이다.
3. `{% wireview_header %}`가 모든 페이지에 `<script defer src="{% static ... %}">`를 순서 고정해
   내보낸다.
4. 파일은 자기 이름을 자기가 쓴다: `window.wireview.hooks.Chart = { mounted() {...} }`.
   파일명에서 이름을 가져오려면 ES module과 `export default`가 필요하고, 그러면 (가)의 보장이
   비동기 import 경합으로 되돌아간다. **이름을 한 번 더 적는 대가로 순서 보장을 산다.**
5. `manage.py check`에 `wireview.W011` — 양방향으로 본다.
   - 템플릿에 `wire-hook="X"`가 있는데 수집된 훅에 `X`가 없다
   - 수집된 훅 파일이 staticfiles로 해석되지 않는다(앱이 `INSTALLED_APPS`에 없는 등)
   템플릿 스캔은 정규식이라 동적 이름은 못 본다. **경고이지 오류가 아닌 이유가 그것**이고,
   체크 문서에 그렇게 적는다.
6. `WIREVIEW["COLLECT_HOOKS"]` (기본 `True`). 자기 번들에 넣는 프로젝트가 끄는 스위치.

### AC1을 정직하게 읽으면

인수 조건은 "컴포넌트 옆에 둔 훅 파일이 **별도 등록 없이** 동작한다"이다. A가 없애는 것은
**배선**이다 — `<script>` 태그를 어디에 넣을지, 번들 어디에 넣을지, 번들이 wireview보다 먼저
실행되지 않게 하는 것. 파일은 여전히 자기 훅 이름을 한 번 적는다. 그것까지 없애려면 ES module이
필요하고 §4-4의 대가를 치른다. **이슈의 AC를 그대로 통과했다고 말하려면 AC1을 이 뜻으로 고쳐 적어야 한다.**

## 5. 결정할 것

1. **규약 경로를 앱의 static(`<app>/static/<app_label>/hooks/*.js`)으로 할 것인가.** 이는
   "컴포넌트 파일 옆"이 아니라 "앱 옆"이다. Phoenix처럼 컴포넌트 소스 옆(`myapp/live/hooks/`)에
   두려면 wireview가 그 디렉터리를 staticfiles finder로 노출해야 하고, `collectstatic`과
   해시가 거기에 딸려 온다 — 할 수는 있지만 **정적 파일 체계를 하나 더 만드는 일**이다.
2. **모든 페이지에 전부 내보내는 것을 받아들일 것인가.** §2-(나) 때문에 이것이 맞다고 보지만,
   대가는 훅 파일 수만큼의 `<script>` 태그다. 받아들이지 않는다면 boost 이동에서 훅이 없는
   경우를 어떻게 다룰지가 새로 풀 문제가 된다.
3. **파일이 자기 이름을 쓰는 것(권장)인가, ES module + 파일명 규약인가.** 후자는 보일러플레이트를
   완전히 없애는 대신 join 순서 보장을 비동기 import 위에 다시 세운다.

## 6. 착수하면 답이 있어야 하는 것들

- **`DOMContentLoaded` 지연이 무엇을 늦추는가.** 지금은 파싱이 끝나자마자 join이 나간다. 뒤로
  미루면 첫 렌더가 늦어질 수 있다 — `bench/`로 재고, 차이가 의미 있으면 "이미 로드된 문서"
  경로(`document.readyState !== "loading"`)를 함께 둔다.
- **훅 파일이 404일 때.** 지금은 훅이 없는 것과 구별되지 않는다. 태그가 프로젝트에서 왔으므로
  `manage.py check`가 먼저 잡지만, 배포 뒤 깨진 경우는 콘솔뿐이다.
- **이름 충돌.** 앱 둘이 같은 훅 이름을 쓰면 나중에 실행된 쪽이 이긴다. 컴포넌트 이름이 전역
  등록이라 같은 문제를 이미 갖고 있고(`wireview.W003`), 같은 모양으로 잡는다.
- **`_live_sessions`와의 관계.** 훅 파일은 경계와 무관하다(전역이므로). 경계 뒤의 훅 코드가
  공개 페이지에도 실린다는 뜻이고, **훅 파일에 비밀을 두면 안 된다**는 문장이 문서에 필요하다.
- **이름 붙이기.** 파일명과 훅 이름이 다를 수 있다(파일이 자기 이름을 쓰므로). 규약으로
  같게 두되 강제하지 않는 편이 맞다고 보지만, 체크의 템플릿 스캔은 *등록된 이름*을 본다.

## 7. 먼저 확인해야 할 것: 훅에는 아직 사용자가 없다

`wire-hook`을 쓰는 템플릿이 이 저장소에 **하나도 없다.** `examples/` 열 개에도, `testproj/`의
픽스처에도, E2E 어디에도 없다. 검색하면 `docs/features/hooks.md`와 빌드된 번들만 나온다.

서버 쪽은 테스트가 있다 — `tests/test_hooks.py`가 `handle_hook_event`와 `push_event`를 단위로
검사한다. 검증된 적이 없는 것은 **클라이언트 절반**이다: `mountHooks`, 수명주기 여섯 콜백,
morph 전후의 `beforeUpdate`/`updated`, `disconnected`/`reconnected`, `pushEvent`의 왕복.

이것이 이 이슈에 주는 뜻은 분명하다. **등록을 쉽게 만들기 전에 등록된 훅이 실제로 도는지를
먼저 알아야 한다.** 지금 상태에서 GAP-032를 구현하면 "훅 파일을 자동으로 싣는 장치"의 정확성을
"훅이 원래 동작한다"는 검증되지 않은 전제 위에 올리는 것이고, 실패하면 어느 쪽이 틀렸는지
가려낼 수 없다.

그래서 순서를 이렇게 제안한다.

1. 훅을 쓰는 **예제 하나**와 그 E2E를 먼저 만든다(`examples/` 규약: 개념 하나 + tests.py 하나 +
   README 하나). 지금 방식대로 — 손으로 `window.wireview.hooks.X = {...}`를 등록하는 페이지로.
   이것이 훅의 첫 사용자이자 클라이언트 절반의 첫 검증이다.
2. 그 위에서 GAP-032를 한다. 그러면 "손으로 등록한 것과 자동 수집이 같은 결과를 낸다"가
   **대조군이 있는 단언**이 된다.

1이 2보다 값이 크고 위험이 작다. 1만 하고 멈춰도 저장소는 나아진다.
