# 키 없는 "키 기반" comprehension — 항목을 내용으로 짝짓는다

> **제안 — 결정 대기.** 결정할 것은 §8에 모았고 이슈에도 올렸다. 코드는 아직 손대지 않았다.

## 0. 요약

이슈는 "위치가 아니라 **키**로 맞춘다"고 적었다. 이 메모의 제안은 **키를 쓰지 않는 것**이다.

wireview는 렌더 **결과**(항목마다의 dynamics 목록)를 서로 비교해서 diff를 만든다. 두 항목의 dynamics가 같으면
두 항목의 HTML도 같다 — static은 comprehension 전체가 공유하기 때문이다. 그러므로 옛 목록과 새 목록의 항목을
**내용으로** 짝지으면 키가 하던 일(이동·삽입·삭제를 그 항목만의 변경으로 만드는 일)을 템플릿 문법 없이 할 수 있다.
중복 키 계약도, 키 있는 항목과 없는 항목이 섞일 때의 계약도 생기지 않는다. 같은 내용의 두 항목은 어느 쪽으로
짝지어도 복원된 HTML이 같기 때문이다.

| 변경 | 항목 50개: 지금 → 제안 | 항목 500개: 지금 → 제안 |
|---|---:|---:|
| 앞에 하나 삽입 | 1,546 → 68 | 16,398 → 70 |
| 가운데 하나 삽입 | 815 → 78 | 8,392 → 82 |
| 첫 항목 삭제 | 1,480 → 32 | 16,330 → 34 |
| 마지막을 맨 앞으로 | 1,511 → 41 | 16,362 → 44 |
| 전체 뒤집기 | 1,511 → 463 | 16,362 → 4,914 |
| 항목 하나의 텍스트 / 끝에 추가 | 52 / 58 → **같음** | 53 / 60 → **같음** |

단위는 diff 본문의 JSON 바이트이고 서명 상태 슬롯은 뺐다(§6). 가장 비싼 경우인 앞 삽입에서 **diff 계산도
지금보다 빠르다**(50개 6.2µs → 2.5µs, 500개 66µs → 23µs). 지금 방식이 바뀐 항목을 전부 직렬화하는 반면,
제안 방식은 공통 앞뒤를 `==`로 잘라 내고 가운데만 본다.

## 1. 지금 무엇이 일어나는가

`Comprehension.diff`(`wireview/core/rendered.py`)는 새 목록의 i번째를 옛 목록의 i번째와 비교하고, 다르면 그
항목의 dynamics **전체**를 `{"u": {"i": [...]}, "n": 개수}`에 담는다. 앞에 하나를 끼우면 모든 i에서 비교가
어긋나므로 목록 전체가 다시 나간다. djust 메모 §3의 2,162B가 그것이다.

## 2. Phoenix는 어떻게 하는가 — 소스로 확인한 것

`phoenixframework/phoenix_live_view` `assets/js/phoenix_live_view/rendered.js`의 `mergeKeyed`
(2026-09-08 커밋 `1357afe` 기준):

- 키는 **wire에 실리지 않는다.** 템플릿의 `:key`는 서버가 옛 항목과 새 항목을 짝짓는 데만 쓰인다.
- comprehension 부분 diff는 `{"k": {"<새 위치>": entry, ..., "kc": 개수, "km": 이동 여부}}`이다. entry는 셋 중 하나다.
  - 숫자 `j`: 옛 위치 j의 항목을 그대로 가져온다(이동, 내용 변경 없음)
  - `[j, diff]`: 옛 위치 j의 항목을 가져와 diff를 적용한다(이동하면서 변경)
  - 객체: 같은 위치에서 diff를 적용한다
- 이동이 있으면(`km`) 클라이언트는 옛 상태를 먼저 복제한 뒤 적용한다. 앞선 쓰기가 나중에 읽을 자리를 덮지 않게 하려는 것이다.

Phoenix가 키를 템플릿에서 받아야 하는 이유는 diff 엔진의 성격에 있다고 본다. Phoenix는 렌더 결과가 아니라 assigns의
변경 추적(`__changed__`)으로 무엇을 다시 렌더할지 정하므로, 옛 항목과 새 항목이 같은 것인지 물을 기준이 템플릿
밖에서 와야 한다. **이것은 우리의 해석이고 Phoenix 엔진 소스로 확인하지는 않았다.** wireview는 매번 전체를 렌더하고
결과를 비교하므로, 그 기준은 이미 손에 있다.

가져올 것은 **"옛 위치를 가리키고, 새 내용만 싣는다"는 wire 모양**이다. 바꿀 것은 둘이다. 새 위치마다 entry를
하나씩 보내는 대신 연속 구간을 `[시작, 길이]` 하나로 접는다(앞 삽입 1회가 Phoenix에서는 숫자 50개이고, 여기서는 구간
하나다). 짝짓기 기준은 키가 아니라 내용이다.

## 3. 제안하는 wire 형태

comprehension 슬롯의 부분 diff 값에 네 번째 형태를 더한다.

```json
{"k": [[0, 3], {"d": ["new", "7"]}, [3, 47]]}
```

- `k`는 새 목록을 앞에서부터 채우는 **구간의 목록**이다.
  - `[j, len]`(정수 두 개): 옛 목록의 `j`번째부터 `len`개를 그대로 옮긴다
  - `{"d": [...]}`: 새 항목 하나. 값은 지금 `u`의 값과 같은 dynamics 목록이다
- 새 목록의 길이는 구간 길이의 합이다. `n`은 두지 않는다 — 합과 다를 수 있는 값을 하나 더 두면 불일치의 계약을 정해야 한다.
- 구간은 **옛 목록을 읽기만 한다.** 클라이언트는 옛 배열을 그대로 두고 새 배열을 만든 뒤 바꿔 끼운다. Phoenix의 `km` 복제가 필요 없다.

지금의 세 형태(`{"s","d"}` 전체, `{"u","n"}` 위치 갱신, 문자열)는 그대로 남는다. 판별은 `k`가 배열이고 `s`가 없는 것.

### 3-1. 서버는 어느 형태를 고르는가

두 형태 중 **다시 보내는 항목이 적은 쪽**, 같으면 **위치 형태**. 위치 형태로 충분한 변경(제자리 편집, 끝에 추가,
끝에서 삭제)은 지금과 **바이트까지 같다**. 짝짓기 형태가 나가는 것은 그것이 실제로 항목을 덜 보낼 때뿐이다.

짝짓기 절차:

1. 앞에서부터 `old[i] == new[i]`인 구간과 뒤에서부터 같은 구간을 잘라 낸다(`==` 비교만, 해시 없음).
2. 남은 가운데의 옛 항목을 **내용 식별자**(dynamics를 재귀적으로 tuple로 만든 것) → 옛 위치 목록의 사전에 넣는다.
3. 새 가운데를 앞에서부터 돌며 사전에서 꺼낸다. 있으면 `[j, 1]`(앞 구간과 이어지면 합친다), 없으면 `{"d": ...}`.
4. 같은 내용의 항목이 여럿이면 앞에서부터 꺼낸다. 어느 것을 꺼내도 HTML이 같으므로 이 선택은 정확성에 영향이 없다.

앞 삽입·중간 삽입·삭제·한 항목 이동은 1단계에서 거의 다 끝나므로 해시를 거의 하지 않는다. 전체 뒤집기처럼 가운데가
긴 경우에만 목록 크기만큼 해시한다. 그 경우도 render_diff 전체 시간(500개에서 약 4.3ms)에서 차이가 측정 잡음 안이었다.

### 3-2. 폴백 계약

| 상황 | 보내는 것 | 지금과 비교 |
|---|---|---|
| 항목 템플릿이 바뀜(static 다름) | comprehension 전체 `{"s","d"}` | 같다 |
| 빈 목록에서 채워짐 | 전체(빈 comprehension은 static이 없다) | 같다 |
| 목록이 비워짐 | 빈 comprehension 전체 `{"s": [], "d": []}`(static이 달라지므로) | 같다 |
| 루프가 균일하지 않아 문자열이 됨(`{% empty %}`, 항목별로 다른 구조) | 문자열 전체 | 같다 |
| 중복 내용 | 짝짓기에 참여, 앞에서부터 | 새 계약 필요 없음 |
| 항목에 위치 의존 값(`forloop.counter`, `cycle`)이 있음 | 삽입 한 번에 모든 항목이 달라지므로 위치 형태로 폴백 | 같다(이득 없음) |
| 이동하면서 내용도 바뀐 항목 | 그 항목만 `{"d": ...}`로 전체 | 지금과 같은 입자(항목 단위) |

마지막 줄이 Phoenix의 `[j, diff]`에 해당하는 자리다. 항목 **안의** 부분 diff는 지금도 없다(바뀐 항목은 dynamics
전체를 보낸다). 넣을지는 항목이 무거운 실제 템플릿에서 잰 뒤 정한다 — 그때 필요한 것이 바로 키다(내용이 바뀐 항목을
옛 항목과 짝지을 기준). 즉 **키는 이 GAP의 전제가 아니라 그 다음 단계의 선택지**다.

### 3-3. 중첩

- 항목 안의 `{% if %}` 블록, 중첩 comprehension, LiveComponent 참조 `{"c": id}`는 모두 내용 식별자에 포함된다. 참조는 id만 담으므로
  자식이 바뀌어도 부모 항목은 같은 것으로 짝지어진다 — 자식 HTML은 자식 렌더로만 오간다는 기존 계약 그대로다.
- 짝짓기는 comprehension마다 독립적이다. 바깥 목록의 항목을 옮기면서 그 안의 목록이 바뀌면 바깥 항목 하나가 `{"d"}`로 나간다.

## 4. 템플릿에서의 선언

**없음.** 기존 템플릿이 그대로 이득을 본다. 이슈의 "`{% for %}` 위의 태그인지 속성인지"라는 질문은 §3-2 마지막 줄의
다음 단계로 넘긴다.

DOM 쪽 정체성은 지금처럼 idiomorph가 맡는다. `rendered.mjs`는 HTML 문자열을 복원할 뿐이고, 요소 이동을 보존하려면
항목 루트에 `id`를 두는 것이 지금도 맞는 조언이다(`docs/features/html-diff.md` 주의사항에 한 줄 더한다).

## 5. 버전이 섞일 때 (AC3)

| 서버 | 클라이언트 | 결과 |
|---|---|---|
| 새 | 새 | 짝짓기 형태 사용 |
| 옛 | 새 | 옛 서버는 `k`를 보내지 않는다. 새 클라이언트는 기존 형태를 그대로 읽는다 |
| 새 | **옛** | **깨진다.** 옛 `applyPartial`은 `{"k": ...}`를 모르는 값으로 보고 슬롯에 그대로 넣으며, `renderDynamic`이 `String(value)`로 `[object Object]`를 그린다 |

셋째 줄은 실제로 일어난다. 롤링 배포 중 옛 JS로 열린 페이지가 끊겼다가 새 서버에 재연결하는 경우, 그리고 CDN이
옛 `wireview.min.js`를 들고 있는 경우다. 그래서 **클라이언트가 먼저 말한다**:

- 클라이언트가 WebSocket URL에 `?vsn=2`를 붙인다(Phoenix와 같은 이름).
- 컨슈머가 connect 때 `scope["query_string"]`에서 읽어 연결 상태에 둔다. `vsn`이 없거나 2 미만이면 **위치 형태만** 보낸다.
- 그래서 옛 클라이언트는 지금과 바이트까지 같은 메시지를 받는다.

지금 프로토콜에는 버전 개념이 없다. 이 필드가 첫 버전 신호가 되므로 `docs/implementation/wire-protocol.md` §7에 규칙을
함께 적는다: **클라이언트가 이해한다고 말한 형태만 보낸다.** 서버 쪽 기본값은 "아무것도 모르는 클라이언트"다.

`mount()` 테스트 하네스는 최신 버전으로 동작한다. 이 결정은 `Comprehension.diff`까지 내려가야 하므로, 전역 상태가 아니라
`render_diff`에서 `get_diff`를 거쳐 명시적 인자로 내린다.

## 6. 바닥은 여전히 서명 상태다

위 표는 서명 상태 슬롯을 뺀 수치다. 실제 프레임에서 `BenchList`는 항목을 상태로 들고 있어 토큰이 50개일 때 약 600B,
500개일 때 약 3.8KB다. 앞 삽입 한 번의 전체 프레임은 2,165B → 685B(50개), 20,261B → 3,935B(500개)가 된다.
**500개 목록에서 남은 바이트의 98%가 토큰이다.** 항목을 상태에 두는 컴포넌트에는 항목을 조회로 옮기거나
`_temporary_assigns`를 쓰라는 기존 조언(`html-diff.md`)이 이 GAP 뒤에 더 중요해진다. 이 GAP은 그 부분을 건드리지 않는다.

## 7. 검증 계획

**먼저 delta round-trip 테스트를 깐다(이 GAP 전에, 독립 커밋).** 짝짓기 형태의 정확성은 결국 "서버가 만든 diff를
실제 클라이언트 코드에 적용하면 새 렌더와 같은 HTML이 나오는가" 하나다.

- pytest가 시드 고정 난수로 목록 변이를 연속 적용한다: 삽입(앞·중간·끝), 삭제, 이동, 뒤집기, 중복 내용 삽입,
  항목 안 조건 토글, 비우기·채우기, 중첩 목록 변경.
- 매 단계에서 `Rendered` 전체와 부분 diff를 만들고, 전체 시퀀스를 JSON 한 덩어리로 `node`의 작은 드라이버
  (`tests/js/roundtrip.mjs`)에 한 번 넘긴다. 드라이버는 실제 `rendered.mjs`로 적용하고 매 단계의 HTML을 돌려준다.
- pytest가 그것을 서버의 `to_html()`과 비교한다. node가 없으면 skip하지 않고 **실패**한다 — CI test 잡은 이미 JS를 빌드하므로 node가 있다.
- 이 테스트는 지금의 위치 형태에도 그대로 돈다. 그래서 기존 diff에 대한 안전망이 먼저 생기고, 짝짓기 형태는 그 위에 얹는다.

AC4의 나머지:

- `tests/js/rendered.test.mjs`: `k` 적용의 단위 테스트(구간, 새 항목, 옛 배열을 읽기만 하는지, 빈 결과).
- `tests/test_diff_stability.py`: 위치 형태로 충분한 변경은 짝짓기 도입 전과 **같은 바이트**라는 것, `vsn` 없는 연결은 `k`를 받지 않는다는 것.

AC5(벤치): `bench/payload.py`에 `list.insert_front`, `list.insert_middle`, `list.remove_first`, `list.move_last_to_first`,
`list.reverse`를 50개와 500개로 더한다. **시나리오를 먼저 커밋하고** 그 커밋을 `BASE`로 `make bench-compare`를 돌려
전후 수치를 `docs/features/html-diff.md` 실측 절에 남긴다.

## 8. 결정할 것

1. **키 대신 내용으로 짝짓는다.** 템플릿 문법을 만들지 않는다. 키는 이동하면서 바뀐 항목의 부분 diff가 필요하다고
   실측이 말할 때의 다음 단계로 둔다.
2. **AC2를 다시 쓴다.** "키가 없는 기존 템플릿은 지금과 똑같이 동작한다"는 키가 있다는 전제 위의 문장이다. 이 제안에서는
   모든 템플릿이 새 형태의 대상이다. 대신: "위치 형태로 충분한 변경은 지금과 바이트까지 같고, `vsn`을 말하지 않는 클라이언트는
   지금과 바이트까지 같은 메시지를 받는다."
3. **wire 형태** `{"k": [[j, len] | {"d": [...]}, ...]}`, `n` 없음.
4. **버전 신호** `?vsn=2`. 이 저장소의 첫 프로토콜 버전 필드다.
5. **순서**: round-trip 테스트 → 벤치 시나리오 → 구현. 셋 다 별도 커밋.

## 9. 버린 것

- **템플릿 키(`{% for item in items key=item.id %}` 류)를 이번에 넣기.** 키가 주는 것은 내용 짝짓기가 이미 준다(§0).
  남는 이득은 이동하면서 바뀐 항목의 항목 내부 diff인데, 지금은 제자리 편집조차 항목 단위로 보낸다. 입자를 줄이는 일은 이
  GAP과 따로 잰다. 그리고 키는 계약 셋(중복·혼합·누락)을 데려온다. djust가 DJE-050·DJE-051로 그 셋을 따로 다룬다.
- **Phoenix의 새 위치별 entry.** 옮긴 항목 하나마다 숫자 하나라 앞 삽입이 O(n)이다. 구간으로 접으면 O(구간 수)다.
- **LIS로 최소 이동 계산.** HTML 문자열을 다시 만드는 쪽에는 "이동" 연산이 없다. 구간 목록이 곧 결과이고, DOM 이동은 idiomorph가 id로 한다.
- **JSON 직렬화를 식별자로 쓰기.** 시제품 1판이 그렇게 했고 앞 삽입 diff가 50개에 87µs, 500개에 867µs였다(지금 방식의 14배).
  앞뒤 자르기와 tuple 식별자로 바꾸자 2.5µs / 23µs가 됐다.
- **옛 클라이언트를 감지하지 않고 배포 순서로 해결.** JS와 서버가 한 패키지라도 이미 열린 페이지가 재연결하는 창은 막을 수 없다.
