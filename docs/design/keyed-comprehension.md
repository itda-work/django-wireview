## 0. 요약

이슈는 "위치가 아니라 **키**로 맞춘다"고 적었다. 이 메모의 제안은 **키를 쓰지 않는 것**이다.

wireview는 렌더 **결과**(항목마다의 dynamics 목록)를 서로 비교해서 diff를 만든다. 두 항목의 dynamics가 같으면
두 항목의 HTML도 같다 — static은 comprehension 전체가 공유하고, 중첩 블록·목록의 static은 dynamics 안에 들어 있기
때문이다. 그러므로 옛 목록과 새 목록의 항목을 **내용으로** 짝지으면 키가 하던 일 중 **전송량에 관한 몫**(이동·삽입·
삭제를 그 항목만의 변경으로 만드는 일)을 템플릿 문법 없이 할 수 있다. 같은 내용의 두 항목은 어느 쪽으로 짝지어도
복원된 HTML이 같으므로 중복 키 계약도, 키 있는 항목과 없는 항목이 섞일 때의 계약도 생기지 않는다.

키가 하던 일 중 **DOM 정체성**(어느 요소가 옮겨 갔는가)은 이 층의 일이 아니다. 지금도 idiomorph가 id로 한다(§4).

| 변경 | 항목 50개: 지금 → 제안 | 항목 500개: 지금 → 제안 |
|---|---:|---:|
| 앞에 하나 삽입 | 1,546 → 59 | 16,398 → 60 |
| 가운데 하나 삽입 | 815 → 69 | 8,392 → 72 |
| 첫 항목 삭제 | 1,480 → 23 | 16,330 → 24 |
| 마지막을 맨 앞으로 | 1,511 → 32 | 16,362 → 34 |
| 전체 뒤집기 | 1,511 → 454 | 16,362 → 4,904 |
| 항목 하나의 텍스트 / 끝에 추가 | **같음** | **같음** |

단위는 comprehension 슬롯 하나의 diff JSON 바이트다(서명 상태 슬롯과 render 메시지 봉투 제외). **시제품으로 잰 값이고
최종 구현의 실측이 아니다.** 첫 판의 표는 제안에서 뺀 `n`을 시제품이 여전히 싣고 있던 값이었다. 위 값은 리뷰가 `n`을 빼고
다시 계산한 것이다(리뷰 원문 중요 4). 구현 뒤 §7의 벤치가 이 표를 대체한다.

## 1. 지금 무엇이 일어나는가

`Comprehension.diff`(`wireview/core/rendered.py`)는 새 목록의 i번째를 옛 목록의 i번째와 비교하고, 다르면 그
항목의 dynamics **전체**를 `{"u": {"i": [...]}, "n": 개수}`에 담는다. 앞에 하나를 끼우면 모든 i에서 비교가
어긋나므로 목록 전체가 다시 나간다. djust 메모 §3의 2,162B가 그것이다.

## 2. Phoenix는 어떻게 하는가 — 소스로 확인한 것

`phoenixframework/phoenix_live_view` `assets/js/phoenix_live_view/rendered.js`의 `mergeKeyed`
(2026-09-08 커밋 `1357afe` 기준):

- 키는 **wire에 실리지 않는다.** 템플릿의 `:key`는 서버가 옛 항목과 새 항목을 짝짓는 데만 쓰인다.
- comprehension 부분 diff는 `{"k": {"<새 위치>": entry, ..., "kc": 개수, "km": 이동 여부}}`이다. entry는 셋 중 하나다.
  - 숫자 `j`: 옛 위치 j의 항목을 그대로 가져온다(이동, 내용 변경 없음)
  - `[j, diff]`: 옛 위치 j의 항목을 가져와 diff를 적용한다(이동하면서 변경)
  - 객체: 같은 위치에서 diff를 적용한다
- 이동이 있으면(`km`) 클라이언트는 옛 상태를 먼저 복제한 뒤 적용한다. 앞선 쓰기가 나중에 읽을 자리를 덮지 않게 하려는 것이다.

Phoenix가 키를 템플릿에서 받아야 하는 이유는 diff 엔진의 성격에 있다고 본다. Phoenix는 렌더 결과가 아니라 assigns의
변경 추적(`__changed__`)으로 무엇을 다시 렌더할지 정하므로, 옛 항목과 새 항목이 같은 것인지 물을 기준이 템플릿
밖에서 와야 한다. **이것은 우리의 해석이고 Phoenix 엔진 소스로 확인하지는 않았다.** wireview는 매번 전체를 렌더하고
결과를 비교하므로, 그 기준은 이미 손에 있다.

가져올 것은 **"옛 위치를 가리키고, 새 내용만 싣는다"는 wire 모양**이다. 바꿀 것은 둘이다. 새 위치마다 entry를
하나씩 보내는 대신 연속 구간을 `[시작, 길이]` 하나로 접는다(앞 삽입 1회가 Phoenix에서는 숫자 50개이고, 여기서는 구간
하나다). 짝짓기 기준은 키가 아니라 내용이다.

## 3. 제안하는 wire 형태

comprehension 슬롯의 부분 diff 값에 네 번째 형태를 더한다.

```json
{"k": [[0, 3], {"d": ["new", "7"]}, [3, 47]]}
```

- `k`는 새 목록을 앞에서부터 채우는 **구간의 목록**이다.
  - `[j, len]`(정수 두 개): 옛 목록의 `j`번째부터 `len`개를 그대로 옮긴다
  - `{"d": [...]}`: 새 항목 하나. 값은 지금 `u`의 값과 같은 dynamics 목록이다
- 새 목록의 길이는 구간 길이와 새 항목 수의 합이다. `n`은 두지 않는다 — 합과 다를 수 있는 값을 하나 더 두면 불일치의 계약을 정해야 한다.
- 구간은 **옛 목록을 읽기만 한다.** 클라이언트는 옛 배열을 그대로 두고 새 배열을 만든 뒤 바꿔 끼운다. Phoenix의 `km` 복제가 필요 없다.

지금의 세 형태(`{"s","d"}` 전체, `{"u","n"}` 위치 갱신, 문자열)는 그대로 남는다. 판별은 `k`가 배열이고 `s`가 없는 것.

### 3-1. 서버는 어느 형태를 고르는가

**직렬화 바이트가 작은 쪽, 같으면 위치 형태.** 첫 판은 "다시 보내는 항목 수"로 골랐는데, `k`는 변하지 않은 앞뒤도
구간으로 적어야 하고 `u`는 생략하므로 둘은 어긋난다. 1,002개 목록에서 가운데 두 항목만 맞바꾸면 위치 형태가 46B,
짝짓기 형태가 49B인데 항목 수 규칙은 49B를 고른다(리뷰 중요 1).

직렬화 없이 답이 정해지는 경우는 먼저 거른다. 이 둘은 **지금과 바이트까지 같다**:

- 길이가 같고 바뀐 위치가 하나 이하 — 위치 형태가 항상 작거나 같다. 바뀐 위치는 **세기만** 하고 payload는 만들지 않는다.
- 옛 목록이 새 목록의 앞부분이거나 그 반대(끝에 추가, 끝에서 삭제) — 위치 형태로 고정한다. 두 형태의 크기가 몇
  바이트 안이라 비교할 이득보다 지금과 같은 바이트를 지키는 쪽이 낫다.

나머지는 두 후보를 만들어 JSON 길이로 비교한다. 두 후보 모두에 들어가는 새 항목 dynamics는 한 번만 재고 차이만 비교하는
것이 구현의 목표다. 이 비교가 벤치의 이벤트당 CPU에 보이면 그때 추정으로 바꾼다 — 그 경우 계약을 "바이트 감소 보장"에서
"추정"으로 낮추고 문서에 적는다.

짝짓기 절차:

1. 앞에서부터 `old[i] == new[i]`인 구간과 뒤에서부터 같은 구간을 잘라 낸다(`==` 비교만, 해시 없음).
2. 남은 가운데의 옛 항목을 **내용 식별자**(dynamics를 재귀적으로 tuple로 만든 것) → 옛 위치들의 `deque` 사전에 넣는다.
3. 새 가운데를 앞에서부터 돌며 `popleft()`로 꺼낸다. 있으면 `[j, 1]`(앞 구간과 이어지면 합친다), 없으면 `{"d": ...}`.
4. 같은 내용의 항목이 여럿이면 앞에서부터 꺼낸다. 어느 것을 꺼내도 HTML이 같으므로 이 선택은 정확성에 영향이 없다.

비용은 **가운데에 남은 항목들의 dynamics 전체 크기에 선형**(해시 사전 기준 기대값)이다. 앞 삽입·중간 삽입·삭제는 1단계에서
가운데가 한두 항목으로 줄어든다. 그러나 **한 항목을 끝에서 맨 앞으로 옮기는 것만으로도 공통 앞뒤가 사라져 전 항목을 해시한다**
— 첫 판의 "한 항목 이동은 1단계에서 끝난다"는 틀렸다. 중복 버킷을 `list.pop(0)`으로 꺼내던 시제품은 같은 내용 32,000개의
회전에 73ms가 걸렸다(O(n²), 리뷰 중요 2). `deque`로 없어지는 결함이고, 벤치에 중복 회전·고유 회전·깊은 중첩 항목·대부분
바뀐 목록을 넣어 선형인지와 tuple 식별자의 임시 메모리를 함께 잰다.

### 3-2. 폴백 계약

파서가 먼저 슬롯의 종류를 정하고, 짝짓기는 그 뒤에만 선택지가 된다.

| 상황 | 보내는 것 | 지금과 비교 |
|---|---|---|
| 슬롯의 이전 값이 comprehension이 아니거나 항목 static이 다름(템플릿 변경, 빈 목록에서 채워짐, 목록이 비워짐) | 새 comprehension 전체 `{"s","d"}` | 같다 |
| 렌더된 루프가 균일하지 않음(`{% empty %}` 절이 렌더됨, 항목마다 다른 구조, `{% cycle %}`처럼 마커 없이 static을 바꾸는 태그) | 문자열 전체 | 같다 |
| 균일한 루프, 내용이 바뀜 | §3-1의 규칙으로 `u` 또는 `k` | 선택지가 하나 늘었다 |
| 중복 내용 | 짝짓기에 참여, 앞에서부터 | 새 계약 필요 없음 |
| 항목에 위치 의존 dynamic(`{{ forloop.counter }}`) | 삽입 뒤의 항목 내용이 대개 달라진다. 비용 비교가 알아서 고른다 | 반복 패턴이 같으면 재사용은 여전히 정확하다 |
| 항목 안에 서명 상태 토큰(중첩 `{% component %}`) | 토큰이 바뀐 항목은 다른 내용이다 | 많은 항목의 토큰이 한 렌더에서 갱신되면 이득이 사라진다 |
| 이동하면서 내용도 바뀐 항목 | 그 항목만 `{"d": ...}`로 전체 | 지금과 같은 입자(항목 단위) |

서명 상태를 식별자에서 빼서 토큰이 바뀐 항목을 재사용하게 만들면 **오래된 토큰을 클라이언트에 되살린다.** 금지한다.

마지막 줄이 Phoenix의 `[j, diff]`에 해당하는 자리다. 항목 **안의** 부분 diff는 지금도 없다(바뀐 항목은 dynamics
전체를 보낸다). 넣을지는 항목이 무거운 실제 템플릿에서 잰 뒤 정한다 — 그때 필요한 것이 바로 키다(내용이 바뀐 항목을
옛 항목과 짝지을 기준). 즉 **키는 이 GAP의 전제가 아니라 그 다음 단계의 선택지**다.

### 3-3. 중첩

- 항목 안의 `{% if %}` 블록, 중첩 comprehension, LiveComponent 참조 `{"c": id}`는 모두 내용 식별자에 포함된다. 참조는 id만 담으므로
  자식이 바뀌어도 부모 항목은 같은 것으로 짝지어진다. 같은 id가 시간에 걸쳐 같은 HTML을 뜻하지는 않지만, 클라이언트가
  자식 diff를 먼저 적용하고 부모를 만들 때 현재 자식 HTML로 풀기 때문에 기존 계약 그대로다.
- 짝짓기는 comprehension마다 독립적이다. 바깥 목록의 항목을 옮기면서 그 안의 목록이 바뀌면 바깥 항목 하나가 `{"d"}`로 나간다.
- 블록 부분 갱신 `{"p": …}` 안의 comprehension에도 `k`가 나올 수 있다. 짝짓기 여부는 슬롯 깊이와 상관없이 같은 규칙이다.

### 3-4. 구간의 범위 계약

- 구간은 **직전에 완성된 comprehension**(클라이언트가 이 diff를 받기 직전에 들고 있던 항목 배열)을 기준으로 한다.
- `[j, len]`은 `j ≥ 0`, `len > 0`, `j + len ≤ 옛 길이`. 새 목록이 비면 comprehension 전체가 나가므로(§3-2 첫 줄) `k: []`는 만들지 않는다.
- 생성 알고리즘은 **한 옛 위치를 두 번 쓰지 않는다.** 그래서 클라이언트가 옛 항목 객체를 새 배열에서 참조로 재사용해도 공유로 인한 오염이 없다.
  항목 내부 diff나 중복 참조를 나중에 허용하면 이 전제를 다시 본다.
- 클라이언트는 범위를 벗어난 구간을 받으면 적용하지 않고 오류를 로그한다(조용히 잘라 쓰지 않는다).
- 서버 스냅샷(`Rendered.to_dict()`/`from_dict()`)은 지금처럼 `{"s","d"}` 전체 구조만 저장한다. `k`는 전송 형태이지 저장 형태가 아니다.

## 4. 템플릿에서의 선언

**없음.** 기존 템플릿이 그대로 이득을 본다. 이슈의 "`{% for %}` 위의 태그인지 속성인지"라는 질문은 §3-2의
다음 단계로 넘긴다.

DOM 쪽 정체성은 지금처럼 idiomorph가 맡는다. `rendered.mjs`는 HTML 문자열을 복원할 뿐이고, 같은 최종 HTML이면 `k`든 `u`든
DOM에 주는 정보가 같다. 그래서 이 설계가 포커스·훅·스트림을 **새로** 깨뜨리지는 않는다. 반대로 **새로 지켜 주지도 않는다** —
id 없는 같은 마크업 항목의 입력 상태는 지금처럼 위치로 morph된다. 요소 이동을 보존하려면 항목 루트에 `id`를 두는 것이
지금도 맞는 조언이다(`docs/features/html-diff.md` 주의사항에 한 줄 더한다).

## 5. 버전이 섞일 때 (AC3)

| 서버 | 클라이언트 | 결과 |
|---|---|---|
| 새 | 새 | 짝짓기 형태 사용 |
| 옛 | 새 | 옛 서버는 `k`를 보내지 않는다. 새 클라이언트는 기존 형태를 그대로 읽는다 |
| 새 | **옛** | **깨진다.** 옛 `applyPartial`은 `{"k": ...}`를 모르는 값으로 보고 슬롯에 그대로 넣으며, `renderDynamic`이 `String(value)`로 `[object Object]`를 그린다 |

셋째 줄은 실제로 일어난다. 롤링 배포 중 옛 JS로 열린 페이지가 끊겼다가 새 서버에 재연결하는 경우, 그리고 CDN이
옛 `wireview.min.js`를 들고 있는 경우다. 그래서 **클라이언트가 먼저 말한다**:

- 클라이언트가 WebSocket URL에 `?vsn=2`를 붙인다(Phoenix와 같은 이름).
- 컨슈머는 connect 때 `scope["query_string"]`에서 읽어 **연결별 전용 필드**(예: `protocol_version`)에 둔다. 페이지의 검색 조건인
  `consumer.query_string`과 섞지 않는다 — 그 값은 `command_query_string`과 boost 이동(`wireview.js`의 `newLocation`)이 바꾸므로,
  섞으면 페이지 이동이 프로토콜 능력을 바꾼다. join의 서명 봉투의 `v`와도 별개다.
- 해석은 보수적으로: 없음·정수 아님·음수·여러 번 나옴은 모두 **0**(아무것도 모르는 클라이언트). 0이면 **위치 형태만** 보내므로
  옛 클라이언트는 지금과 바이트까지 같은 메시지를 받는다. 앞으로의 규칙은 "값 이하의 모든 형태를 이해한다"다.
- 재연결은 같은 JS가 같은 URL로 다시 협상한다. 같은 소켓 안의 boost 이동은 능력을 유지하고, 새로 join한 컴포넌트는 늘 전체 렌더로 시작한다.
- 이 필드는 wire-protocol.md §6 세션 상태 표에 더한다. 세션을 프로세스 밖으로 옮길 때(GAP-027) 함께 옮겨야 하는 목록이다.

지금 프로토콜에는 버전 개념이 없다. 이 필드가 첫 버전 신호가 되므로 `docs/implementation/wire-protocol.md` §7에 규칙을
함께 적는다: **클라이언트가 이해한다고 말한 형태만 보낸다.** 서버 쪽 기본값은 "아무것도 모르는 클라이언트"다.

능력은 전역 상태가 아니라 명시적 인자로 렌더 경로 전체에 내린다: `consumer._render_tree` → `component._render_diff` →
`wire.render_diff` → `get_diff` → `changes` → `Rendered.diff`/`Comprehension.diff`. 최상위 comprehension만이 아니라 블록 안쪽과
LiveComponent 렌더에도 닿아야 한다. `mount()` 하네스는 최신 버전으로 동작하므로 **하네스만으로 검사하면 컨슈머에서 인자가
빠진 것을 못 잡는다** — 테스트는 컨슈머 경로로도 한다(§7).

## 6. 바닥은 여전히 서명 상태다

위 표는 서명 상태 슬롯을 뺀 수치다. `BenchList`는 항목을 상태로 들고 있어 서명 토큰이 50개일 때 약 600B, 500개일 때
약 3.8KB다(diff 객체 JSON 기준, render 메시지 봉투 제외). 500개 목록의 앞 삽입에서 **diff 객체 바이트의 대부분이 토큰이다.**
정확한 비율은 구현 뒤 render 메시지 단위로 다시 잰다.

토큰을 줄이는 방법은 목록을 **서명 상태에서 빼는 것**이다: `_exclude_fields`에 넣거나 필드 대신 조회로 만들고, 재연결 때
제외한 항목을 다시 불러오는 경로를 컴포넌트가 가진다. **`_temporary_assigns`는 이 렌더의 토큰을 줄이지 않는다.** 컨슈머는
diff를 만든 **뒤에** 필드를 비우므로(`consumer._render_tree`), 그 렌더의 토큰에는 목록이 그대로 들어간다(리뷰 중요 3, 실행으로
확인됨). 첫 판의 조언은 틀렸다. `_temporary_assigns`의 효과는 렌더 뒤 메모리를 비우는 것이고, 다음 이벤트에서 목록을 다시
채우면 그때 또 큰 상태를 서명한다. 이 GAP은 토큰을 건드리지 않는다.

## 7. 검증 계획

**delta round-trip 테스트는 깔았다**(7593fc3, `tests/test_diff_roundtrip.py` + `tests/js/roundtrip.mjs`). 시드 고정 난수로
목록을 편집하며 매 단계 서버 diff를 실제 `rendered.mjs`로 적용하고, 클라이언트 HTML이 서버 렌더와 같은지 본다. 결함 넷을
주입해 모두 실패하는 것을 확인했다. 지금은 위치 형태에 대한 안전망이다.

리뷰가 짚은 빈틈과 그 처리:

| 빈틈 | 처리 | 언제 |
|---|---|---|
| 드라이버가 `buildHtml`을 resolver 없이 불러 LiveComponent 참조가 빈 문자열이 된다 | 난수 변이에 자식 참조와 자식 HTML 변경을 넣고, 드라이버가 실제 클라이언트처럼 자식을 먼저 적용한 뒤 resolver로 부모를 만든다 | 지금 |
| 블록 부분 갱신 안의 comprehension 갱신을 강제하지 않는다 | 템플릿에 그 구조를 넣고 경로 가드가 요구한다 | 지금 |

AC4의 나머지:

- `tests/test_diff_stability.py`: §3-1의 두 fast path가 도입 전과 **같은 바이트**라는 것, 가운데 두 항목 맞바꾸기처럼 `u`가 더 작은 경우 `u`를 고르는 것.

AC5(벤치): `bench/payload.py`에 `list.insert_front`, `list.insert_middle`, `list.remove_first`, `list.move_last_to_first`,
`list.reverse`, `list.swap_middle`을 50개와 500개로, CPU 쪽에 중복 회전과 깊은 중첩 항목을 더한다. **시나리오를 먼저 커밋하고**
그 커밋을 `BASE`로 `make bench-compare`를 돌려 전후 수치를 `docs/features/html-diff.md` 실측 절에 남긴다. 단위는 셋으로
나눈다: 서명 포함 diff 객체 JSON, render 메시지 JSON, 이벤트당 CPU. 첫 판의 "diff 계산 6.2µs → 2.5µs"는 평평한 comprehension의
마이크로벤치였고 전체 렌더 벤치와 섞지 않는다.

## 8. 결정할 것

1. **키 대신 내용으로 짝짓는다.** 템플릿 문법을 만들지 않는다. 키는 이동하면서 바뀐 항목의 부분 diff가 필요하다고
   실측이 말할 때의 다음 단계로 둔다.
2. **AC2를 다시 쓴다.** "키가 없는 기존 템플릿은 지금과 똑같이 동작한다"는 키가 있다는 전제 위의 문장이다. 이 제안에서는
   모든 템플릿이 새 형태의 대상이다. 대신: "§3-1의 fast path(한 위치 이하 변경, 끝 추가·삭제)는 지금과 바이트까지 같고,
   `vsn`을 말하지 않는 클라이언트는 지금과 바이트까지 같은 메시지를 받는다."
3. **wire 형태** `{"k": [[j, len] | {"d": [...]}, ...]}`, `n` 없음, 범위 계약은 §3-4.
4. **선택 규칙**은 직렬화 바이트, 같으면 위치 형태(§3-1).
5. **버전 신호** `?vsn=2`, 연결별 전용 필드, 보수적 해석(§5). 이 저장소의 첫 프로토콜 버전 필드다.
6. **순서**: round-trip 보강(§7 "지금") → 벤치 시나리오 → 구현. 각각 별도 커밋.

## 9. 버린 것

- **템플릿 키(`{% for item in items key=item.id %}` 류)를 이번에 넣기.** 전송량에 관해 키가 주는 것은 내용 짝짓기가 이미 준다(§0).
  남는 이득은 이동하면서 바뀐 항목의 항목 내부 diff인데, 지금은 제자리 편집조차 항목 단위로 보낸다. 입자를 줄이는 일은 이
  GAP과 따로 잰다. 그리고 키는 계약 셋(중복·혼합·누락)을 데려온다. djust가 DJE-050·DJE-051로 그 셋을 따로 다룬다.
- **다시 보내는 항목 수로 형태 고르기.** 첫 판의 규칙. 구간 메타데이터를 세지 않아 더 큰 쪽을 고르는 반례가 있다(§3-1).
- **Phoenix의 새 위치별 entry.** 옮긴 항목 하나마다 숫자 하나라 앞 삽입이 O(n)이다. 구간으로 접으면 O(구간 수)다.
- **LIS로 최소 이동 계산.** HTML 문자열을 다시 만드는 쪽에는 "이동" 연산이 없다. 구간 목록이 곧 결과이고, DOM 이동은 idiomorph가 id로 한다.
- **JSON 직렬화를 식별자로 쓰기.** 시제품 1판이 그렇게 했고 앞 삽입 diff가 50개에 87µs, 500개에 867µs였다(지금 방식의 14배).
  앞뒤 자르기와 tuple 식별자로 바꾸자 2.5µs / 23µs가 됐다(평평한 comprehension 마이크로벤치).
- **서명 상태를 식별자에서 빼기.** 토큰이 바뀐 항목을 재사용하게 되어 오래된 토큰을 되살린다(§3-2).
- **옛 클라이언트를 감지하지 않고 배포 순서로 해결.** JS와 서버가 한 패키지라도 이미 열린 페이지가 재연결하는 창은 막을 수 없다.

## 부록 A. 측정 재현

djust 메모 부록 A의 방식(`bench.settings`로 `mount()` → `render_diff()`)에 `Comprehension.diff`를 시제품으로 바꿔
끼워 쟀다. 2026-09-19, macOS, Python 3.12, Django 6.0, `BenchList`(항목마다 `{% if %}` 하나와 변수 둘). 시제품의
핵심은 §3-1 절차이고(단 첫 판 시제품은 `n`을 싣고, 항목 수 규칙을 쓰고, 중복 버킷에 `list.pop(0)`을 썼다), 저장소에
커밋하지 않았다. `n`을 뺀 재계산과 반례 측정은 리뷰 원문의 부록에 스크립트째 있다. 구현 커밋의 벤치 시나리오(§7)가
이 표를 대체한다.
