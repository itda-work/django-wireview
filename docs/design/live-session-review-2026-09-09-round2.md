## 2. 남은 발견 — 심각도 순

### A. [높음] LiveComponent는 부모 렌더 도중 등록·렌더된다. 뒤늦은 훅으로는 출력 유출을 막지 못한다

**대상:** `live-session.md:127-130` (§3-5), AC1·AC3.

**문제:** 새 문장의 “LiveComponent는 부모 렌더 **뒤** 별도 경로로 등록”은 사실과 반대다. 부모 렌더 후 실행되는 것은 joined/update 큐다.

**코드 근거:**

1. `templatetags/wireview.py:788-795`는 부모 템플릿 평가 중 `repo.build_live_component()`를 호출하고 바로 자식을 `_render()`한다.
2. `repository.py:159-166`은 그 build 안에서 부모 id를 지정하고 저장소에 등록한 뒤 joined 대기 큐에 넣는다.
3. `consumer.py:99-104`는 부모 render 전송 후 대기 큐를 처리한다. `repository.py:199-209`의 joined/update가 이 시점이다.

**남는 실패:** “네 경로에 훅 적용”을 joined 큐 처리 시점에 구현하면, WS 이벤트가 새로 만든 자식의 민감한 HTML이 이미 부모 render에 포함된 뒤다. HTTP 보호 AC2는 이후 WS 렌더까지 대신 보호하지 않는다. 서버 저장소에서 자식을 지워도 이미 보낸 출력은 회수되지 않는다.

재join도 별도 문제다. `repository.py:82-90`은 기존 객체를 먼저 변경하고, `221`은 children을 먼저 병합한다. AC3의 “등록되지 않는다”만으로 기존 객체 변경과 children 잔존을 롤백하는지 명확하지 않다.

**제안:** 훅 통과 전에 자식 HTML·상태·부작용을 외부로 내보내지 않는다는 조건을 AC에 넣어야 한다. 동기 템플릿 렌더와 async 훅의 연결 방법도 정해야 한다. 재join halt 시 기존 객체를 보존할지 제거할지 선택하고, 거절된 요청의 필드/children/대기 메일이 후속 요청에 사용되지 않는지 검증해야 한다.

### B. [높음] #76은 TimestampSigner 도입만이 아니라 전체 발급·갱신·거절 프로토콜 변경이다

**대상:** #76의 고칠 방향, `live-session.md` §3-2·§5, AC1·AC4·AC5.

**문제:** 요약에 있는 “클래스, 만료, 구형 전환, 재join 검사”는 방향은 맞지만 다음 계약이 빠졌다.

- **실제 만료:** Django의 `TimestampSigner.unsign(..., max_age=None)`은 기본으로 만료를 검사하지 않는다. 이번 임시 실행에서 시각을 1000→100000으로 바꿔도 `unsign_object(token)`은 통과했고, `max_age=60`일 때만 `SignatureExpired`였다. 서명자 교체만으로 해결됐다고 판정하면 안 된다.
- **구형 우회:** 현재 `core/state.py:51-54`는 legacy JSON 서명과 compact 서명을 받는다. 새 봉투 검사 실패·만료 후 구형 파서로 fallback하거나, 클래스 미결합 구형 상태를 계속 보호 join에 허용하면 #76은 열린 채다. 버전과 용도별 salt, 허용 기간/대상, 실패 시 재인증·재로드 규칙이 필요하다.
- **발급 경로:** `templatetags/wireview.py:26-44`의 동일 `sign_state(component)`가 HTTP와 WS 렌더에 사용된다. 최초 HTTP 봉투뿐 아니라 이벤트 후 새 data-state도 원래 검증된 정책·인증 문맥을 유지해야 한다. 클라이언트가 별도로 보낸 이름/현재 페이지 메타로 권한을 높여 재서명하면 안 된다.
- **재연결:** `wireview.js:90-105,938-959`는 재연결 시 DOM의 저장된 상태를 재전송한다. 오래 유휴 상태인 페이지는 마지막 상태가 만료될 수 있다. 현재 join의 unsign은 `consumer.py:81-84`에서 try 바깥이다. 만료 예외만 추가하면 연결 종료/반복 재연결 또는 화면 복원 실패가 생길 수 있다. 유효한 인증으로 상태를 안전하게 갱신할지, 전체 로드할지, 편집 중 폼을 어떻게 처리할지 정해야 한다.
- **boost/cache:** history의 body에는 과거 data-state가 들어 있다. 정상 쿠키로 fetch한 새 HTML과 과거 캐시를 섞어 쓰거나, 구형 상태를 “복구” 명목으로 새 권한으로 재발급해서는 안 된다. 모든 root/children 봉투를 동일 기준으로 검증해야 한다.
- **클래스/객체 일치:** 외부 `name`, children의 외부 id 키, 봉투 내부 id/정규 클래스, 기존 repository 객체가 일치해야 한다. FQN·app alias는 서버에서 정규화해야 한다. 같은 id의 기존 LiveComponent를 재사용하는 `repository.py:132-142`도 일반 재join과 별도로 확인해야 한다.

**제안:** #76 완료 조건에 구형/만료/변조 봉투의 거절, 유휴 후 재연결의 정상 복구, HTTP→WS 갱신→재연결, children, boost history, 혼합 버전 배포 테스트를 넣어야 한다. #58의 정책/인증 봉투 확장 지점도 #76 설계 때 합의해야 한다.

Timestamp를 매 렌더 갱신하면 상태가 같아도 다음 초의 data-state는 달라진다. 현재 서명 결정성과 no-op diff에 영향이 있다(`core/state.py:7-10`). 동적 마커를 유지하고, 토큰 갱신 주기와 무변경 렌더 테스트를 정하되 성능 저하 수치를 실측 없이 단정하지는 말아야 한다.

### C. [높음] 인증 세대의 표현과 폐기 규약이 없어 AC6을 통과하고도 재연결이 살아날 수 있다

**대상:** `live-session.md:147-154` (§5-1), AC6, #76 봉투와의 연계.

**문제:** 기존 탭에서 이벤트 하나가 거절되는 것은 로그아웃 폐기의 일부다. 로그아웃한 세션으로 새 연결을 만드는 경우, 권한 회수, 같은 사용자 재로그인은 명시되어 있지 않다.

**근거:**

- Django signed-cookie 백엔드의 `delete()`는 로컬 세션 데이터와 쿠키를 비우며, 발급한 모든 과거 쿠키를 서버 저장소에서 폐기하지 않는다(`django/contrib/sessions/backends/signed_cookies.py:62-70`).
- 실제 임시 실행에서 합성 세션의 쿠키 값을 보관하고 `flush()`한 다음, 이전 값으로 새 `SessionStore`를 만들자 `{'review_marker': 'old-session'}`이 복원됐다. 실제 사용자 세션을 사용한 실험은 아니다.
- 따라서 이런 백엔드에서 disconnect만 하고 이전 인증 증표의 폐기를 별도로 하지 않으면, 보관한 쿠키/봉투로 재연결할 여지가 남는다. 서버 저장소형 백엔드도 오래된 scope/캐시만 비교하면 충분하지 않다.
- **세션 키 원문을 data-state에 넣는 구현도 피해야 한다.** §5-1의 “세션 키를 결합”을 그대로 직렬화하라는 뜻으로 구현하면, 서명은 암호화가 아니므로 DOM에서 Django 세션 인증 증표를 읽을 수 있게 된다. 이는 현재 코드에 존재하는 유출이 아니라 제안 문구의 위험한 구현 가능성이다.

**제안:** 지원 세션 백엔드와 실제 폐기 확인 방식을 정해야 한다. 봉투에는 원래 세션 쿠키를 공개하는 대신 서버가 확인할 수 있는 전용 식별자/단방향 결합값 등을 사용해야 한다. 그 결합값 자체도 폐기 저장소를 대체하지는 않는다.

AC6에 로그아웃 후 새 WS, 같은 사용자 재로그인 시 이전 봉투, 익명→로그인, 사용자/tenant 변경, staff 권한 회수, 진행 중 구독 출력 차단을 추가해야 한다. 클라이언트의 disconnect 수신에만 의존해서는 안 된다. 객체 id·params·이벤트 payload에 대한 현재 권한 검증은 앱이 별도로 수행한다는 경계도 필요하다. 같은 정책 이름/신원이라는 사실만으로 객체 접근 권한이 생기지 않는다.

### D. [높음] HTTP 보호를 요구했지만 예제의 RequireStaff를 HTTP에 적용하는 계약은 없다

**대상:** `live-session.md` §3-1·§3-4·§4, AC2.

**문제:** “Django 인증을 실제로 거는 데코레이터”라는 추가 문장만으로는 페이지 정책과 HTTP 권한이 같아지지 않는다. 현재 API는 `live_session("admin", on_mount=[RequireStaff, AuditTrail])`뿐이고, 훅은 `on_mount(component, params, session)`인 async 프로토콜이다.

**근거:** `_run_on_mount_hooks()`(`core/component.py:531-554`)은 이미 존재하는 컴포넌트 객체를 인자로 받는다. 반면 뷰 진입 시점에는 템플릿 안에 어떤 객체가 생길지 아직 정해지지 않았다. `templatetags/wireview.py:60-81`은 동기 build/render 경로다. 단순 login_required 수준의 검사만 붙이면 로그인한 비staff에게 admin HTTP 렌더를 허용할 수 있다.

**제안:** request 기반 페이지 접근 검사와 component 훅을 분리할지, 컴포넌트 렌더 전 동일 정책을 실행할지 명시해야 한다. 객체가 필요한 훅과 AuditTrail의 HTTP/WS 실행 횟수도 정해야 한다. AC2는 익명뿐 아니라 **인증됐지만 인가되지 않은 사용자**에게 HTML·상태가 반환되지 않는 경우를 포함해야 한다. 상세 구현을 지금 정할 필요는 없지만, 현재 예제만으로 보호가 완성된다는 인상을 주어서는 안 된다.

### E. [높음] #77의 키 변경은 단일 프로세스 충돌 수정이며 분산 업로드 해결책이 아니다

**대상:** `session-extraction.md` §2·§4 단계 0/3·§5, #77 고칠 방향.

**문제:** 단계 0 검증에는 다중 프로세스 업로드가 들어가 있지만 작업은 연결 단위 키 변경이다. 프로세스 B의 dict가 비어 있는 문제는 키를 `(connection_id, component_id)`로 바꿔도 똑같다. 단계 3에는 여전히 “세션 상태나 외부 저장소로 / 0단계에서 확인한 실패가 사라지는지”가 남아 단계 0의 버그 수정과 모순된다.

**근거:** `views.py:32,44,71,114-117`은 프로세스 로컬 저장과 조회다. `143-154`는 로컬 파일 경로와 entry를 갱신한다. 컴포넌트 안에 레지스트리는 이미 있으므로 세션 객체로 옮기는 것은 HTTP의 소유 워커 접근을 제공하지 않는다.

**#77에서 빠진 계약:**

- 소유 워커 라우팅/RPC 또는 공유 레지스트리·파일 저장소 중 실제 접근 방법.
- 서버가 발급한 소유권 식별자를 HTTP 토큰·요청·통지 그룹에 일관되게 결합. 현재 토큰은 `component_id:config_name:ref`뿐이다(`features/uploads.py:335-336`).
- leave/disconnect의 소유권 확인과 진행 중 HTTP 청크와의 경합 처리.
- 재연결 후 새 connection id가 생겼을 때 이전 업로드를 취소할지, 검증 후 인계할지. 동일 연결에서 같은 component id를 재마운트할 때도 오래된 토큰/청크가 새 인스턴스에 붙지 않는 세대 구분.
- 정상 disconnect가 없는 프로세스 사망의 파일/등록 만료와 정리.

**제안:** 충돌/정리 수정과 분산 접근 수정을 독립 하위 작업으로 나눠도 좋지만, 키 변경만으로 #77 전체가 해결됐다고 하지 않아야 한다. 분산 업로드 수정이 세션 export/import 뒤로 다시 밀리지 않도록 단계 3을 정리해야 한다.

### F. [중간] AC5의 세 경로 테스트만으로 내비게이션 검증은 충분하지 않다

**대상:** `live-session.md` §3-3, AC5.

본문은 메타 없음·최종 redirect·검증 전 params 차단까지 요구하는데 AC5에는 입력 경로만 있다. 아래 경우가 빠졌다.

- **같은 정책, 다른 인증 문맥:** 다른 탭에서 로그인하거나 사용자/tenant가 바뀐 뒤 같은 이름의 페이지를 fetch한다. 새 봉투와 연결 문맥 불일치 때 안전하게 재인증/전체 로드할지 정해야 한다. join 거절만 하면 권한 상승은 막더라도 정상 내비게이션은 깨진다.
- **과거 캐시와 응답 경쟁:** 느린 이전 fetch가 새 페이지를 덮거나, 검증 전 예약된 캐시 morph가 나중에 실행되는 경우. `replaceBodyContent()`는 requestAnimationFrame을 예약한다(`wireview-boost.js:138-147`).
- **메타 없음/구형/만료 및 redirect 최종 URL:** 실패 시 public으로 자동 강등하거나 과거 메타를 그대로 쓰지 않아야 한다.
- **서버 replace:** `wireview.js:244-250`은 fetch 없이 history를 바꾸고 params를 보낸다. 현재 문서의 “합류점”을 자동으로 통과하지 않는다. 현재 화면의 URL/params 갱신으로 한정할지, 다른 정책 경계를 넘는 사용을 막을지 명시해야 한다. URL만 바뀌었다고 실제 보호 페이지가 로드된 것은 아니므로 이를 곧바로 권한 상승으로 단정하지는 않는다.

**제안:** 입력 경로뿐 아니라 위 결과/실패 조건을 AC5에 연결해야 한다. AC 번호도 갱신해야 한다. §3-3은 지금도 내비게이션 조건을 “AC2”라고 부르지만 현재 AC2는 HTTP 보호다.

### G. [중간] 세션 추출의 입력 계약에 기존 단정이 남아 있다

**대상:** `session-extraction.md:14` (§1), §2·§3.

“Outbound와 컴포넌트 저장소만 있으면 성립”은 뒤의 인증 scope 전달·Broker/mail 설명과 맞지 않는다. `WireviewMeta`의 Broker, 업로드 등록의 channel 조건, session mail과 fan-out 수신이 필요한 사실은 그대로다(`core/meta.py:76-88,457-470`, `consumer.py:524`).

**제안:** 추상화된 인증 문맥, 세션 주소, Broker/메일 입력과 직렬 처리 수명을 명시해야 한다. “WebSocket 전송에 독립적으로 만들 수 있다”와 “현재 Outbound만 주입하면 충분하다”를 구분해야 한다. 이번 §3의 mailbox 설명은 수정 방향이 맞다.

### H. [중간] 메모리 외삽 경고와 착수 기준 표가 여전히 충돌한다

**대상:** `session-extraction.md:109-122` (§5).

수치의 조건과 외삽을 제대로 설명했지만 표에는 여전히 “~~메모리~~ … deflate를 끄면 당분간 병목이 아니다”가 있다. 측정한 2,000개에서 50.6 KB/connection인 사실은 운영 메모리 예산·목표 연결 수의 병목 여부를 결정하지 않는다.

“버퍼는 포함되지 않았다”도 과도하다. `bench/ws.py:236,247,269`는 baseline과 joined의 프로세스 RSS 차이를 측정하므로 **그 실험에서 실제 할당된 버퍼 비용은 포함**된다. 측정하지 않은 것은 다른 부하/백프레셔에서 추가로 자랄 버퍼다.

**제안:** 메모리를 기준에서 삭제하지 말고 목표 배포 구성과 연결 수에서 다시 판단한다는 앞 문장과 일치시켜야 한다. 약 4배는 연결당 증분 RSS 비율에 근거한 예상이며, 같은 총 RSS 예산에서 최대 연결 수를 4배까지 실측한 결과와 구분해야 한다.

## 3. AC1~AC8 충분성 판정

**현재 AC는 필요하지만 충분하지 않다.** 원래 지적된 기본 공격은 훨씬 잘 다룬다. 다만 AC의 포괄적 문구를 특정 예제 테스트 하나로 축소하면 다음 구현도 통과할 수 있다.

| AC | 추가할 검증/명확화 |
|---|---|
| AC1 | 자식 생성뿐 아니라 재사용/update·재join에서 정책 보존, 거절된 자식의 HTML이 부모 출력으로 나가지 않음. |
| AC2 | 비로그인뿐 아니라 비staff 등 인가 실패, HTTP 보호 정책과 WS 정책의 일치. |
| AC3 | 기존 id 재join 실패의 상태 처리, children·자식·구독·작업·대기 메일 롤백. user_event 외 hook_event/params/upload 경로도 거절 객체에 도달하지 않음. |
| AC4 | root/children 각각의 버전·용도·만료·클래스·id 검증, 구형 fallback 차단, 인증 문맥이 다른 정상 봉투의 재사용 거절. |
| AC5 | 캐시/메타 누락/최종 redirect/응답 경쟁/같은 정책의 인증 변경, server replace 의미, 검증 전 DOM·params 전파 없음. |
| AC6 | 기존 연결뿐 아니라 로그아웃 후 재연결, 권한 회수, 재로그인·익명 전환, 지원 백엔드별 폐기, 폐기 후 구독 출력. |
| AC7 | 컴포넌트 훅·HTTP 접근 정책·객체별 이벤트 인가의 역할과 책임을 구분. |
| AC8 | 구현 완료 정의로서는 타당하다. 다른 AC의 빈 조건을 대신 채우지는 않는다. |

예컨대 **TimestampSigner에 max_age를 주지 않는 구현**, **기존 탭만 끊고 보관한 signed-cookie로 새 WS는 허용하는 구현**, **세 경로의 정상 내비게이션만 시험하고 캐시 예약 경쟁은 방치하는 구현**은 현재 명시된 대표 테스트들을 통과할 수 있다.

## 4. 요청한 코드 서술 대조 및 새 문장 오류

| 문장/위치 | 확인 결과 |
|---|---|
| component_remove는 브라우저 명령만 보냄 | **맞음.** `consumer.py:358-360`. 단 “기존 오류 경로를 쓰면 항상 객체가 살아 있다”는 표현은 build/등록 이후 실패한 경우로 한정해야 한다. 등록 전 실패에는 잔존 객체가 없다. |
| LiveComponent가 부모 렌더 뒤 등록됨 | **틀림.** 부모 렌더 도중 등록·렌더하고, 뒤에 joined/update를 호출한다. §2-A 참조. |
| HTTP component 태그가 build 후 즉시 render | **맞음.** `templatetags/wireview.py:60-81`. |
| popstate가 캐시 body를 먼저 morph한 뒤 fetch | **취지는 맞지만 실행 순서는 부정확.** 캐시 morph를 먼저 **예약**하고 fetch를 시작한다. 실제 morph는 requestAnimationFrame에서 실행되므로 반드시 fetch 시작 전에 끝나지 않는다. 1라운드의 같은 축약 표현도 이 구분으로 정정한다. |
| fetch가 title/body만 반영하고 head 메타는 갱신하지 않음 | **맞음.** `wireview-boost.js:215-221`. |
| WireviewMeta.send가 자기 세션도 Broker 경유 | **맞음(전송 시).** pending이면 먼저 큐에 들어간다. 인용한 457행은 send 정의가 아니라 `_do_send`; send는 446행, Broker 호출은 464행이다. |
| 같은 페이지를 탭 둘로 열면 레지스트리를 덮어씀 | **조건 누락.** 같은 component id일 때다. 기본 id는 `rx-{uuid4()}`(`core/component.py:355`)이므로 독립 GET 두 번에서 항상 충돌하지 않는다. 고정 id·캐시/상태 재사용 등의 조건이 필요하다. |
| §3-1 “admin을 자칭할 수 있으면 정책 전체가 장식” | **여전히 부정확.** 서버가 선택된 admin 정책을 강제하면 이름 선택 자체는 인가 통과가 아니다. 새 §3-2의 정확한 위협 설명과 맞춰야 한다. |
| §4 제목의 AC3 | **번호가 낡음.** 역할 구분은 현재 AC7이다. |
| 버퍼가 RSS 수치에 포함되지 않음 | **과도한 단정.** 실험에서 할당된 버퍼는 RSS에 포함된다. §2-H 참조. |

## 5. 착수 순서의 의존성 판정

제시한 **#68 → #75 → #76 → #58**은 실행 순서로 선택할 수 있지만, 모두가 엄격한 직렬 의존성인 것은 아니다.

- **#76은 #68/#75와 독립적으로 클래스 결합 결함을 수정할 수 있다.** 인증 세대·정책 확장을 받을 봉투 버전/발급 문맥 인터페이스를 먼저 합의하면 된다. 현재 취약점 수정을 세션 API 완성까지 기다릴 기술적 이유는 없다.
- **#75의 호출 누락 수정 자체는 #68에 필수 종속되지 않는다.** 현재 훅은 session 인자 기본값을 갖는다(`core/component.py:531-554`). 사용자 기반 훅 호출·halt 동작부터 고칠 수 있다. 다만 session 데이터를 사용하는 훅까지 지원 완료라고 하려면 #68이 필요하다.
- **#58의 안전한 완성에는 #68·#75·#76의 계약이 합류해야 한다.** #76의 구형 형식을 계속 보호 정책에 받아들이는 호환성 규칙은 #58과 충돌하므로, 구현 순서와 별개로 먼저 합의해야 한다. HTTP 정책/자식 렌더 전 훅 설계도 필요하다.
- **#77과 컨슈머 테스트 보강의 독립 처리는 맞다.** 다만 #77에 연결 폐기/업로드 수명이 생기므로 #58의 로그아웃 폐기가 이를 사용하도록 정리 인터페이스를 공유해야 한다. #77을 전체 세션 추출이나 export/import에 종속시킬 필요는 없다.
- **문서는 아직 제시한 순서로 고쳐지지 않았다.** `live-session.md:4`의 선행 목록에 #76이 없고, `161-162`에는 여전히 “#68 → #75 → #58”만 있다. #76은 AC4에서 인용되지만 선행 조건으로 반영되지 않았다.

## 검증 범위

저장소 코드와 문서를 변경하지 않았다. 새 실행 검증은 가상 시각을 사용한 TimestampSigner 만료 동작과 합성 signed-cookie 세션의 flush 후 재사용 두 가지다. 실제 계정·쿠키·외부 서비스는 사용하지 않았다. 나머지는 현재 코드와 수정 diff를 대조한 결과 및 미구현 설계의 실패 시나리오다. 브라우저 E2E·전체 테스트·성능 벤치는 실행하지 않았다.
