> [high-concurrency-options-codex-2026-10-13.md](./high-concurrency-options-codex-2026-10-13.md)에 그대로 뒀다. 첫 판을 같은 모델(high)에
> 적대적으로 두 라운드 리뷰받고 지적 열여덟 가지를 모두 반영했다 — 원문은 [1라운드](./high-concurrency-review-codex-2026-10-13.md)와
> [2라운드](./high-concurrency-review-r2-codex-2026-10-13.md), 무엇을 어떻게 고쳤는지는 §8. 이 메모를 쓰며 새로 잰 것은 없다 — 모든 수치는 출처의 측정이고, 측정일과 조건을 붙였다.

질문은 "Phoenix LiveView보다 동접 처리가 많이 약하지 않은가, 모든 것을 wireview 안에서 풀지 않아도 된다면 어떤 구조가
맞는가"다. 구현 목록이 아니라 목표 구조와, 그 구조를 고르는 데 필요한 측정을 정한다.

## 0. 판정

1. **Phoenix와 비교한 측정은 아직 없다.** 아래의 "가깝다·멀다"는 모두 FastAPI 비교와 wireview 단독 측정에서 온 것이다. Phoenix
   LiveView 1.2.12와 같은 화면을 맞댄 측정, 1만 연결 이상, 정해진 도착률에서 버티는 지속 용량, Linux 운영 환경의 수치가 없다.
   그래서 첫 단계는 측정이고(§6 P0), 그 전에는 어떤 구조도 채택하지 않는다.
2. **부하 종류마다 결론이 다르다.** DB 없는 화면의 측정에서:
   - **공통 갱신의 팬아웃**(모두에게 같은 스트림 항목)은 `Broadcast`로 FastAPI 기준에 가까워졌다(연결 1,000개 18 ms 대 12 ms).
     남은 차이는 프레임 크기(205 B 대 80 B)와 연결마다의 큐다.
   - **같은 화면의 렌더하는 브로드캐스트**는 `shared_render`로 429 → 90 ms가 됐지만 FastAPI(19 ms)와는 아직 멀다. 공유한 뒤의 연결당
     109 µs에서 렌더는 6 µs뿐이고 채널 레이어 수신 47 µs, 트립·디스패치 19 µs가 크다([broadcast-fanout.md](./broadcast-fanout.md) §7-3).
     채널 레이어 47 µs 중 44.5 µs는 InMemory 레이어의 만료 순회라 Redis·NATS에는 없다 — 운영 레이어에서 다시 재야 한다.
   - **같은 화면을 공유하지 않으면**(같은 Board를 구독한 1,000연결에 공지 하나, `shared_render` 끔) 연결당 437 µs이고 그중 렌더 166 µs,
     트립·디스패치 95 µs, diff 88 µs, InMemory 레이어 47 µs다(같은 §7-3). 연결마다 렌더한다는 점은 개인화 렌더와 닮았지만 개인 이벤트의
     측정은 아니다 — 입력·핸들러·인가가 없고 상태는 프로세스 공통 store다.
   - **개인화 이벤트**는 템플릿 전체를 다시 계산하고 diff한다. 인프로세스 측정으로 이벤트 하나가 0.20 ms(스칼라 7개)·0.53 ms(항목 50개)다(§1).
     그 안의 단계별 분해는 개인화 워크로드로 잰 것이 없다 — P0-b가 잰다. Phoenix의 HEEx는 바뀌지 않은 표현식을 계산하지 않으므로 이 부하에서
     구조적 차이가 가장 클 것으로 **추정**한다.
   - **유휴 연결 메모리**는 연결당 수십~백여 KB이고, Phoenix와의 차이는 측정되지 않았다.
   DB·이벤트 루프 지연·GC·느린 클라이언트는 이 측정들에 없다. "약한 곳은 렌더 하나"가 아니라, 렌더·diff·디스패치·채널 레이어가
   부하마다 다른 비율로 나뉜다.
3. **연결 계층만 Phoenix·Go로 바꾸는 하이브리드(C)는 렌더가 지배하는 부하에서는 이득이 작다.** 렌더 작업량은 줄지 않고, 전체 처리량은
   걷어 내는 연결 비용과 새로 생기는 RPC 비용의 차이로 정해진다. 세션 고정·RPC 순서·인증 세대 동기화라는 분산 상태 기계도 생긴다.
   그래서 측정 전에는 보류한다 — 채널 레이어·디스패치가 지배한다고 P0가 보이면 다시 연다.
4. **목표 구조의 뼈대는 "갱신의 종류마다 다른 길"이다(§4).** 모두에게 같은 것은 한 번 렌더하고(`Broadcast`), 같은 화면은 렌더를
   공유하고(`shared_render`), 개인화 화면만 연결마다 렌더한다. 그 뒤의 선택 — 개인화 렌더를 줄이기(변경 추적·결과 캐시), 연결 계층을
   떼어 내기(게이트웨이), 그 화면만 Phoenix LiveView로 두기(공존) — 은 차례로 밟는 계단이 아니라 **P0가 보인 병목에 따라 고르는 분기**다.

## 2. 동접 비용은 넷이다

Codex 원문의 모델을 그대로 쓴다: `CPU ≈ 개인 이벤트율 × 개인 이벤트 비용 + 공통 발행률 × (공유 생성 비용 + 구독자 수 × 전달 비용)`.

| 비용 | wireview의 지금 | Phoenix LiveView 1.2.12 | 차이 |
|------|------|------|------|
| 유휴 연결 | 연결당 55~85 KB(위 조건), 상당 부분이 Python WS 스택 | 빈 BEAM 프로세스 2.6 KB + assigns·transport. 연결당 RSS 공개 수치는 조건이 달라 비교 불가 | **미측정** |
| 공통 갱신의 팬아웃 | `Broadcast`는 한 번 렌더·한 번 직렬화, 연결마다 id만 끼움 | fastlane은 같은 바이트를 transport로. LiveView가 받아 assigns를 바꾸면 view마다 렌더한다 | FastAPI 대비 1.5배. Phoenix 대비 **미측정** |
| 같은 화면의 렌더 | `shared_render`로 렌더 1회, 연결마다 수신·서명·diff·프레임 | view마다 HEEx 계산(바뀐 표현식만)·diff | **미측정.** InMemory 1프로세스 측정에서 우리 쪽 남은 비용은 렌더가 아니라 레이어 수신·디스패치였다. 운영 레이어에서는 다시 잰다 |
| 개인화 이벤트 | 템플릿 전체 재계산 + 이전 렌더와 diff | 바뀌지 않은 표현식은 계산하지 않는다 | 구조적으로 클 것으로 **추정** |
| 코어 활용 | 프로세스 하나가 한 코어. 프로세스 여럿 + Redis·NATS | 한 노드가 모든 코어를 선점 스케줄링 | 프로세스 확장으로 메우되 레이어 왕복·운영 비용이 붙는다 |

2015년의 "Phoenix 2M 연결"은 LiveView 이전의 Channels 실험이고, 40코어·128 GB에 대기만 하는 연결이었다. LiveView가 200만 활성
화면을 처리한다는 근거가 아니다(원문 §1).

## 3. 선택지

A~H의 정의와 근거, 출처는 [Codex 선택지 원문](./high-concurrency-options-codex-2026-10-13.md)이 정본이다. 여기서는 판정과,
원문과 다르게 본 곳만 적는다.

| | 선택지 | 줄이는 것 | 판정 |
|---|------|------|------|
| A | 지금 구조 + `Broadcast`·`shared_render`를 갱신 종류에 맞게 + 코어당 프로세스 | 공통 갱신 | **기준선이자 대조군.** P1에서 계약부터 정한 두 시제품을 더한다 |
| B | 공유 피드만 게이트웨이(Centrifugo·AnyCable·Pushpin·Phoenix Channels)에 | 유휴 연결, 연결당 전달 | **분기 후보.** 이득이 크려면 읽기 전용 구독자의 Python 세션까지 걷어 내야 한다. 소켓을 하나 더 여는 구성은 손해일 수 있다 |
| C | Phoenix가 연결·PubSub, Django가 세션·렌더(RPC) | 연결 메모리 | **보류.** 렌더 작업량을 줄이지 못한다. 레이어·디스패치가 지배한다고 P0가 보이면 다시 연다 |
| D | 특정 실시간 화면을 Phoenix LiveView로, Django는 도메인·ORM·관리자 | 그 화면의 개인화 CPU | **분기 후보, 공존 시제품.** 재작성·두 런타임·권한 철회 설계 비용이 크다. 공식 패턴은 측정 뒤에 정한다 |
| E | Django HTTP 명령 + Mercure/GRIP SSE | 상주 세션 | **제품 범위상 보류.** wireview 전체 대체로는 업로드·renew·양방향 프로토콜을 다시 만들어야 한다. 읽기 전용 피드만이라면 B와 같은 좁은 범위로 함께 비교할 수 있다 |
| F | 렌더를 프로세스·서브인터프리터 풀로 | 코어 활용 | **나중.** 전역 마커 상태(`template_engine`)를 떼어 낸 뒤 프로세스 풀 대조로 |
| G | 렌더 자체를 줄이기: 변경 추적, 메시지 간 결과 캐시(사용자·권한 집단·데이터 revision을 키로), 서버 HTML 조각 캐시, context·조회 중복 제거, 마커 재파싱 줄이기 | 개인화 CPU | **조사 1순위.** 무엇이 이기는지는 P0(b)가 정한다 |
| H | 3.14t·PyPy·Cython·orjson | 국소 | **측정이 가리킬 때만.** JSON은 옛 분해(679.6 µs 중 2.0 µs)에서도, 공유 뒤 분해(109 µs 중 1.4 µs)에서도 작다 |

**원문과 다르게 본 것, 그리고 그 한계.**

- **G를 4위가 아니라 조사 1순위로 올린다.** 개인화 CPU를 Django 안에서 줄이는 길이 여기에 모여 있다(변경 추적만이 아니다 — 결과 캐시·
  조각 캐시·context 정리가 대조군이다). 다만 지금 코드는 "안전하게 건너뛸 수 있는 시간"을 바로 잴 수 있는 상태가 아니다.
  `render_reads`는 부분마다 "초기화된 temporary assign을 읽었는가·다른 것을 읽었는가" 두 불리언만 남기고(필드별 의존 집합이 아니다),
  그 가로채기도 temporary assign을 선언한 클래스에만 설치한다. 마커는 변수를 계산한 **뒤에** 번호를 붙이므로 계산 전의 재사용 키가 아니다.
  `_Reach`는 템플릿이 닿는 곳과 보는 사람 이름을 찾을 뿐 태그·필터·property의 순수성을 증명하지 않는다. 그리고 `_collect_context`는
  템플릿보다 먼저 공개 property를 계산한다. 이 셋은 **재사용할 수 있는 관찰·탐색 부품**이지 보증이 아니다. 그래서 P0(b)의 산출물을
  셋으로 나눈다(§6).
- **A의 두 보강은 "작은 승리"가 아니라 계약부터 정할 설계다.**
  - *자기 메일을 같은 프로세스 안에서 전달하기.* 알림 경로가 Redis에서 가장 느린 이유가 연결마다의 세션 메일 왕복이라는 진단
    ([broadcast-patch.md](./broadcast-patch.md))은 그대로지만, 743 대 379 ms의 차이 전부가 돌아온다는 실험은 아니다. 지금의 Mailbox는 메일끼리의
    순서만이 아니라 **같은 채널에서 알림과 자기 메일이 함께 줄 서는 순서**를 지킨다(`core/transport.py`). 별도의 로컬 큐는 이미 브로커에 줄 선
    알림과의 순서를 잃는다. 인증 철회·reset·release 메일과의 교차도 따져야 한다.
  - *폭주 때 렌더 합치기.* `send_render`는 HTML만 보내지 않는다 — 자식의 `joined`·`update`·`leaving`, 이벤트 `ref`의 답, 업로드 인스턴스,
    구독과 패치 hold를 함께 처리하고, 렌더마다 `after_render`와 temporary assign 초기화가 돈다. 전송만 합치면 계산이 줄지 않고, 계산을
    합치면 관찰 가능한 의미가 바뀐다. 명시적으로 허용한 경로(최신 값만 중요한 알림)부터 시작한다.
- **D는 "채택"이 아니라 공존 시제품 후보다.** 같은 사이트에서 대부분의 화면은 wireview, 개인화 CPU가 지배하는 화면 한둘만 Phoenix
  LiveView로 두는 구성이다. 비용을 줄여 쓰지 않는다: 짧은 토큰을 mount에서 검증하는 것만으로는 긴 연결의 권한 철회가 풀리지 않는다
  (HTTP 첫 응답·연결·업무 이벤트마다의 인가, 만료와 재발급, 철회 메시지가 유실됐을 때의 정책). 같은 Redis·NATS를 쓴다고 메시지가 호환되지
  않는다 — Channels 레이어와 Phoenix PubSub을 잇는 어댑터, 커밋 뒤 발행, revision·다시 스냅샷이 필요하다. 읽기 전용 DB 계정은 Django의
  tenant·권한 필터를 적용하지 않으므로 데이터는 도메인 API로 받는 것을 기본으로 한다. UI·훅·폼·테스트 재작성과 두 런타임의 배포·관측도 남는다.

## 4. 목표 구조

```
브라우저 ──WebSocket──▶ [연결 계층]  wireview ASGI 프로세스 (코어당 하나)
                           │  같은 프레임의 팬아웃: Broadcast (한 번 렌더, id만 끼움)
                           ▼
                        [세션·렌더]   WireviewSession
                           │  ① 모두에게 같은 것   → Broadcast
                           │  ② 같은 화면         → shared_render
                           │  ③ 개인화            → 연결마다 렌더
                           ▼
                        [도메인]      Django ORM·관리자·인증

P0가 보인 병목에 따라 고르는 분기 (어느 쪽으로 가는지는 §6-1의 판정표가 정한다):
  SLO와 자원 예산을 이미 만족       → A 유지. 재설계하지 않는다
  발생기가 목표 주입률을 못 냄       → 측정 무효, 발생기를 고쳐 다시 잰다
  DB 대기·풀 고갈이 한계            → 도메인 경로 조사 (이 메모의 분기 밖)
  개인화 렌더·diff가 한계           → G: 바뀐 것만 계산 / 결과·조각 캐시 (opt-in, 검증 모드)
  유휴 연결 메모리·연결당 전달이 한계 → B: 읽기 전용 피드를 게이트웨이로 (Python 세션까지 걷어 내는 구성)
  레이어 수신·디스패치가 한계        → A 보강(자기 메일 순서 계약) 또는 C 재검토
  한 화면이 G의 채택 뒤에도 SLO 밖   → D: 그 화면만 Phoenix LiveView와 공존
```

갱신 하나가 ①→②→③ 중 가장 앞의 길로 가게 하는 것이 앱의 일이고, 어느 길로 갔는지 보이게 하는 것이 라이브러리의 일이다
(`DEBUG_RENDER_QUERIES`처럼 렌더 경로별 횟수·시간을 로그와 테스트 단언으로).

## 5. 측정이 아니라 추정인 것

- 개인화 이벤트에서 Phoenix와의 차이의 크기.
- G의 효과. 바뀌는 동적 부분의 비율과 그 계산 비용이 화면마다 다르고, 추적 자체의 CPU·메모리 비용이 있다.
- B의 이득. `Broadcast`가 이미 효율적이라 이득은 유휴 연결 메모리와 연결당 전달에 국한될 것으로 본다.
- D의 이득. HEEx 변경 추적의 구조적 이점은 확실하지만, Django 도메인 API 왕복을 더한 p99는 모른다.
- 자기 메일을 로컬로 돌렸을 때 돌아오는 몫.
- 연결당 메모리에서 걷어 낼 수 있는 몫과 Phoenix와의 실제 차이.

### 6-1. 판정표 (P0-0의 산출물)

숫자는 지금 넣지 않는다 — 워크로드와 SLO가 정해져야 정할 수 있다. 대신 **측정 전에** 아래 칸을 채우고 버전을 붙인다. 측정 뒤에 문턱을
고치면 그것은 새 판의 판정표이고, 고친 이유를 적는다.

**유효한 실행.** 정확성·복구 계약을 통과하고, 실제 주입률이 목표의 일정 비율 이상이며, 정해진 기간·반복 수를 채우고, 발생기의 CPU·FD·포트가
한계 밖이고, 운영 레이어·프로세스 수로 돈 실행만 판정에 쓴다. 실패한 실행은 버리지 않고 오류·유실률에 넣는다. 차이가 반복 사이의 흩어짐보다
작으면 이겼다고 하지 않는다(회차의 범위가 겹치면 동률).

| 행 | 전제(이것이 아니면 이 행을 보지 않는다) | 진입 문턱 | 채택 문턱 | 중단 조건 |
|---|---|---|---|---|
| A 유지 | 유효한 실행 | — | 같은 도착률에서 SLO(p95·p99)와 자원 예산(CPU·메모리·큐 나이)을 만족 | — |
| G 렌더 절약 | 개인화 렌더·diff가 이벤트 CPU의 가장 큰 몫 | 안전 후보 CPU 비율 ≥ ___ % | 순 CPU 절감 ≥ ___ %, 0% 건너뜀 오버헤드 ≤ ___ %, 연결당 메모리 증가 ≤ ___ KB, p99 회귀 ≤ ___ %, 검증 모드 전부 통과 | 시제품의 순절감이 진입 문턱의 절반 미만 |
| B 게이트웨이 | 유휴 연결 메모리 또는 연결당 전달이 자원 예산을 넘음 | — | 시스템 전체 메모리 ≥ ___ % 감소, 그동안 CPU 증가 ≤ ___ %, p99 회귀 ≤ ___ % | 이중 연결 구성에서 총 메모리가 줄지 않음 |
| A 보강(P1) | 레이어 수신·디스패치가 가장 큰 몫 | — | 같은 부하에서 CPU ≥ ___ % 감소, 순서·복구 테스트 전부 통과, p99 회귀 없음 | 순서 계약을 지키는 구현이 없음 |
| D 공존 | 한 화면이 G 채택 뒤에도 SLO 밖 | — | 같은 기능·DB 조회 수에서 CPU ≥ ___ % 감소 또는 p99 ≤ SLO, 권한 철회 시험 전부 통과 | 도메인 API 왕복으로 p99가 SLO 밖 |
| 런타임(P5) | 실제 import 뒤 GIL 꺼짐 | — | 4스레드 처리량 ≥ 1스레드 × ___, 단일 스레드 손실 ≤ ___ % | GIL이 다시 켜짐 |

**병목이 둘 이상이면** 가장 큰 몫부터 하나를 없애고 다시 잰다. 두 후보를 함께 비교하는 것은 둘의 비용이 서로 다른 자원일 때만이다(예: G는 CPU, B는 메모리).
**CPU와 메모리가 반대로 움직이면** 자원 예산 중 먼저 넘는 쪽을 따른다 — 예산 안의 자원을 아끼려고 예산 밖의 자원을 늘리지 않는다.

스택 비교(Rails 8 Hotwire, Blazor Server, Spring Boot + Vaadin Flow, Next.js, 원하면 Laravel Livewire)는 P0-a의 하네스를 일반화해

무엇인지). 공정성 규칙은 [bench/README.md](../../bench/README.md#fastapi와-비교)의 것이다.

## 7. 정해야 할 것

- **목표 SLO와 워크로드**(P0-0). 동접 목표, 허용 p95·p99, 활성 비율, 화면의 상태 크기. 원문과 리뷰 모두 이것 없이 합격선을 만들지 않았다.
- **측정 기계.** 1만 연결 이상과 부하 발생기 분리에는 서로 다른 Linux 기계 둘이 필요하다.
- **D를 공식 패턴으로 둘지.** P4의 결과를 본 뒤.
