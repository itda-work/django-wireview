# temporary assign의 초기화를 변경으로 치지 않기

[#111](https://github.com/itda-work/django-wireview/issues/111), GAP-006. 결정됨, 구현 완료.
사용법은 [features/temporary-assigns.md](../features/temporary-assigns.md), 구현은
`wireview/core/render_reads.py`다.

## 1. 문제

`Meta.temporary_assigns` 필드는 렌더 직후 기본값으로 돌아간다. 그러면 목록과 무관한 다음 렌더가
빈 목록을 그리고, diff는 그것을 변경으로 보내 **화면에서 목록이 사라졌다.** 또 그 필드가 서명 상태에
실려, 메모리에서 비운 1만 개가 페이지 속성으로 나갔다.

Phoenix는 초기화를 변경으로 치지 않는다. 컴파일 시점에 각 동적 부분이 어느 assign에 기대는지 알고,
바뀐 assign(`__changed__`)에 기대는 부분만 다시 그린다. wireview의 diff는 **렌더된 값을 비교**하므로
의존 관계를 모른다. 이 설계는 "무엇을 읽었는가"를 렌더 도중에 알아내는 방법이다.

## 2. 결정

1. 초기화한 필드는 `_clear_temporary_assigns()`가 넣은 객체를 기억해 둔다. 다음 렌더에서 **그 객체
   그대로이고 기본값과 같으면 stale**이다. 다시 대입하면 다른 객체가 되고, 제자리에서 고치면 기본값과
   달라진다.
2. stale 필드가 있는 렌더에서만 읽기를 추적한다. 이름을 둘로 가른다.
   - stale: stale 필드, 그리고 stale 필드만 읽어 계산되는 property. 컨텍스트를 만들 때 property를
     하나씩 읽어 보며 가른다.
   - other: 나머지 필드와 property.
3. 읽기는 두 길로 들어온다.
   - 템플릿이 이름으로 읽기(`messages`): 추적하는 렌더는 `TrackingContext`로 그리고, 이것이
     `__getitem__`에서 보고한다.
   - 컴포넌트를 거쳐 읽기(`this.messages`, property 본문의 `self.messages`): `temporary_assigns`를
     선언한 클래스에만 `__getattribute__`를 설치해 보고한다.
4. 템플릿 엔진은 동적 부분마다 슬롯을 열고, 읽기는 가장 안쪽 슬롯에 표시한다. **stale만 읽고 다른
   것은 읽지 않은** 부분의 마커 번호를 모은다.
5. 파서는 그 부분을 `Stale`로 만들고, diff 전에 `Rendered.settle()`이 이전 렌더의 같은 자리 값을
   넣는다. 값이 같으니 보내지 않고, 서버의 마지막 렌더도 브라우저가 가진 것과 같게 남는다.
6. `{% if %}` 블록은 조건이 stale이면 다른 가지를 그리지 않았으므로, 모든 가지에서 참조하는 이름을
   정적으로 모아(`referenced_names`) 다른 필드가 있으면 다시 그린다.
7. 루프 안의 부분은 스스로 값을 지킬 수 없다(항목은 통째로 비교한다). 루프가 정한다. stale 목록을
   도는 루프는 항목을 그대로 둔다.
8. 서명 상태에서 `temporary_assigns` 필드를 뺀다. 다시 join하면 `joined()`가 다시 불러온다.

## 3. 버린 길

**렌더된 조각을 필드별로 기억해 두었다가 다시 쓰기.** 메모리를 줄이려는 기능이 그 필드의 렌더를
따로 들고 있게 된다. 어느 조각이 어느 필드에서 나왔는지 알아야 하는 것도 같아서, 얻는 것이 없다.

**stale 필드 값을 추적용 프록시로 바꿔 넣기.** 처음에는 컨텍스트 값을 callable 래퍼(`StaleRead`)로
바꿔 Django가 부를 때 보고하게 했다. stale 필드만 감싸면 **다른 필드를 읽었는지** 알 수 없다. 중첩
루프(`{% for r in rows %}…{{ messages|length }}`)가 통째로 "그대로"가 되어 `rows`에 새 행이 추가돼도
나가지 않았다(테스트가 잡았다). 모든 값을 감싸면 컨텍스트 값을 직접 읽는 커스텀 태그가 래퍼를 받는다.
`Context.__getitem__`을 가로채는 쪽이 값은 그대로 두고 이름만 본다.

**"stale을 읽었으면 유지"(다른 읽기 무시).** 위와 같은 이유로 실제 변경을 숨긴다. 이 설계는 반대로
**의심스러우면 다시 그린다.** 틀리면 옛날처럼 초기화된 값이 보일 뿐, 바뀐 것이 안 나가지는 않는다.

**Phoenix처럼 템플릿을 컴파일해 의존 관계를 미리 구하기.** Django 템플릿에는 커스텀 태그와 필터가
있고, 그것들이 무엇을 읽는지는 실행해 봐야 안다. 실행 중 추적은 템플릿이 무엇이든 동작한다. 정적
분석은 `{% if %}`의 그리지 않은 가지처럼 실행으로는 볼 수 없는 곳에만 쓴다.

**바깥 슬롯으로 읽기 표시를 올리기.** 한때 슬롯이 닫힐 때 표시를 바깥으로 넘겼다. 블록은 정적 분석이,
루프 안은 루프 자신이 판단하게 되자 이 전파를 없애도 테스트가 하나도 실패하지 않아 걷어냈다.

## 4. 비용

- temporary assign이 없는 컴포넌트: 렌더마다 `_stale_temporaries()`(빈 dict)와, 렌더 시작 때 한 번의
  thread-local 조회가 는다. 동적 노드마다 조회하던 첫 구현은 노드마다 비용이 붙어, 렌더당 한 번 읽어
  `MarkerContext`에 두도록 바꿨다.
- temporary assign이 있는 컴포넌트: 그 클래스의 속성 접근마다 함수 호출 하나. 추적은 stale 필드가 있는
  렌더에서만 켜진다.
- `make bench-compare BASE=f0a9d54 ARGS="--skip-ws"`를 두 번 돌린 결과, 타이밍 차이는 ±20% 안에서
  방향 없이 흔들렸고 페이로드는 같았다. 마지막 회차가 `bench/results/f0a9d54.json`(기준)과
  `bench/results/f0a9d54-dirty.json`(이 변경)이다. 성능을 주장하는 변경이 아니다.

## 5. 한계

- 초기화된 필드와 다른 필드를 함께 읽는 부분은 초기화된 값으로 다시 그린다. `{% if messages %}` 가지
  안에 `{{ count }}`가 있으면 `count`가 바뀔 때 가지가 빠진다. Phoenix도 같다.
- stale 목록을 도는 루프의 항목 안에 다른 값이 있으면 그 값도 멈춘다.
- 비동기 property(코루틴을 돌려주는 것)의 본문은 추적하지 않는다. 컨텍스트를 만들 때 await하므로
  읽기 추적 구간 밖이다. 그런 property는 other로 친다.

## 6. 검증

- `tests/test_temporary_assigns_diff.py`: 경우마다 "남아야 할 것"과 "나가야 할 것"을 짝지은 계약 테스트.
- `tests/test_temporary_assigns_e2e.py`: 브라우저에서 목록이 남는지.
- 변이 검사: settle 제거, 서명 상태 제외 제거, 속성 훅 제거, `TrackingContext` 제거, 제자리 변경 판정
  뒤집기, 블록 정적 분석 제거가 각각 테스트에 걸린다.
